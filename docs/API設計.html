本書は ER図、UI案、DXコア機能 要件定義、 DXコア機能 データ設計 に対応するAPI設計である。 フロントエンドからSupabaseテーブルを直接更新せず、在庫、履歴、監査、通知判定の整合性をAPIとDBトランザクションで保証する。

1. 対象範囲

P0：初回リリース対象

  • ログイン中アカウントと所属研究室の紐付け（溶媒庫は単一で、roomsの行としては持たない）
  • 在庫一覧・詳細・入出庫登録
  • 入出庫履歴の取消・訂正・監査
  • 有効な入出庫履歴から再構成する実績の残量推移
  • 在庫下限値の設定、自室の下限割れ状態表示・下限到達目安のホーム・グラフへの追加
  • 溶媒庫単位の指定数量監視、通知履歴、未確認件数
  • 指定数量1.0以上でのアプリ内通知、未確認件数、状態管理
  • 指定数量監視に必要な溶媒マスタ参照と全体設定の変更・監査

P1：P0安定後に追加する対象

  • 在庫の利用状態の管理
  • 研究室別の利用溶媒管理
  • 全体管理者による溶媒マスタ登録・更新
  • 指定数量超過時の管理者向けメール通知（追加時期・送信先は未決定）

P1の既存APIは本書で先に設計する。メール通知の方式は送信先を確認してから設計する。DX構想の方針に従い、P1の完了をP0リリースの条件にしない。

対象外

  • 発注・購買の提案または自動化
  • 通知エスカレーション
  • 監査レポート自動生成
  • SDS連携、保管期限管理、異常検知
  • 高度な需要予測や補充推奨

2. 設計方針

2-1. 構成

flowchart LR
    UI["Next.js画面"] --> API["Route Handler<br/>/api/v1/*"]
    API --> AUTH["認証・権限確認"]
    AUTH --> QUERY["参照クエリ"]
    AUTH --> RPC["Supabase DB関数<br/>原子的な更新"]
    QUERY --> DB[("PostgreSQL")]
    RPC --> DB
    DB --> TRIGGER["指定数量再判定"]
    TRIGGER --> NOTIFY["notifications"]
    NOTIFY --> APPNOTICE["通知一覧 / 未確認バッジ"]
  • Route Handlerは入力検証、セッション取得、応答整形を担当する。
  • 在庫を変更する処理はDB関数にまとめ、在庫更新と履歴登録の片方だけが成功する状態を作らない。
  • RLSはAPIの権限確認とは別に設定し、誤実装時のデータ露出を防ぐ。
  • 通常のユーザー向けRoute Handlerはセッションに紐付くSupabaseクライアントを使い、service roleでRLSを迂回しない。
  • 指定数量が0.8以上1.0未満の場合はモニターの接近表示のみ、1.0以上の場合はアプリ内通知を作成する。
  • 初回はアプリ内通知のみとする。メール通知は初回後の追加候補で、送信先と方式を決めてから設計する。

2-2. 業務上の決定

項目 APIでの扱い
在庫を超える出庫 409 INSUFFICIENT_STOCK。在庫を0に丸めない
取消・訂正 物理削除せず、履歴の状態変更と監査記録を同一トランザクションで行う
実操作者 共有アカウントと分け、更新系APIで手入力を必須とする
単位 APIは常に solvents.base_unit の数値を入出力する。初回の基準単位はL。画面の1 galは3.8 L、1斗缶は18 Lとし、係数はsettingsから取得する。確定前に換算後のL値を表示する
利用停止 在庫量が0でない場合は 409 INVENTORY_NOT_EMPTY。指定数量集計から実在庫が漏れることを防ぐ
在庫下限 notificationsは作らず、自室のホーム・在庫・グラフに現在状態を表示する
指定数量 単一の溶媒庫内にある全研究室の利用中在庫を合算し、研究室ユーザーへは値も通知も返さない。roomsに種別列は設けない
指定数量通知の再発行 単一溶媒庫の同一種別の未対応通知がある間は抑止。対応済後は倍率が一度1.0未満に戻り、再び1.0以上になった時に新規通知を発行
下限到達日 UIでは「直近N日と同じペースなら」とする目安。発注提案は返さない

3. 共通仕様

3-1. ベースURLとデータ形式

  • ベースURL：/api/v1
  • 認証：Supabase AuthのセッションCookie
  • Content-Type：application/json
  • ID：UUID文字列
  • 日時：ISO 8601、UTCで送受信
  • 数量：JSON number、基準単位で小数第2位まで
  • 表示名・列挙値：APIでは安定した英語コードを返し、日本語表示はUIで変換する

初回リリースの状態・種別コードはDB保存値とAPI値を同じにする。履歴の status は active（有効）／cancelled（取消済）、通知の type は designated_quantity_exceeded（指定数量超過）、通知の status は unread（未確認）／acknowledged（確認済）／resolved（対応済）とする。日本語は画面の表示名であり、DBの検索条件・CHECK制約・APIの送受信には使わない。

画面は入力単位の数量に settings.unit_gal_to_l=3.8 または unit_tokan_to_l=18 を掛け、十進演算でLの小数第2位へ四捨五入してAPIへ送る。既存の「±1 gal」「±1 斗缶」ボタンも同じ係数を使う。丸めたL値が0以下、またはDBの数量範囲を超える場合は422とし、保存値を確定画面に表示する。設定が取得できない場合は換算入力を停止する。表示への逆換算にも同じ係数を使う。

3-2. 成功応答

{
  "data": {},
  "meta": {
    "requestId": "uuid"
  }
}

一覧は meta.nextCursor を使ったカーソルページングとする。 limit の既定値は20、上限は100とする。

3-3. エラー応答

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "現在庫を超える数量は出庫できません。",
    "field": "amount",
    "requestId": "uuid"
  }
}
HTTP 主な用途
400 JSON不正、クエリ不正
401 未ログイン
403 権限不足、他室へのアクセス
404 対象なし。権限外データも情報露出防止のため原則404
409 在庫不足、取消済、バージョン競合、利用停止中、IDEMPOTENCY_KEY_REUSED
422 必須不足、数量範囲不正、不正な状態遷移
500 予期しない内部エラー

3-4. 重複実行防止

すべての状態変更API（POST・PATCHのCommand）は Idempotency-Key: <uuid> を必須とする。UIは1回の操作でUUIDを生成し、通信失敗後の再送では同じキーと同じ入力を使う。別の操作には新しいキーを使う。meta.requestId はHTTP試行ごとの追跡IDであり、再送キーとは別である。

DB内の command_requests は (account_id, idempotency_key) を一意とし、操作種別・対象ID・正規化した引数と成功結果のスナップショットを保持する。DB関数はセッションから操作者を認可した後、実際に受け取った引数から比較値を作り、同じトランザクションでキーを確保して業務更新と結果保存を行う。確定時には結果が必須となるよう、最終行を読み直す遅延制約トリガー等で未完成の要求記録を拒否する。クライアント申告のハッシュだけを信用しない。先行処理中の同一キーは一意制約で確定まで待ち、別SQL文で保存済み結果を読み直す。同じキー・同じ操作と入力なら現在の権限を再確認して当初の成功結果を返し、在庫・履歴・監査・通知を再更新しない。同じキーで操作・対象・入力が異なれば 409 IDEMPOTENCY_KEY_REUSED とする。失敗時はキー確保もロールバックし、再送時に改めて検証する。

指定数量に関わるCommandは、認可後に§7-1の共通ロックを取得してからキーを確保し、続いて対象行をロックする。その他のCommandは認可後にキーを確保してから対象行をロックする。この順序を全てのDB関数で統一する。command_requests は直接SELECT・DMLを許可せず、結果の再取得も認可付きCommand RPC内だけで行う。

3-5. 入力検証

項目 ルール
amount 0より大きい、小数第2位まで
operatorName 1〜100文字、手入力必須
purpose 任意、500文字以下
reason 取消・訂正・利用停止・設定変更で200文字以内、必須
occurredAt 実際の入出庫日時。任意、既定値はサーバー時刻、未来日時と対象在庫の opened_at より前は不可。DB登録日時の created_at とは分けて保存する
threshold・指定数量 在庫下限は0以上またはNULL、指定数量は0より大きい値またはNULL。NULLは未設定であり0で代用しない
warning_ratio・forecast_window_days 前者は0より大きく1より小さい有限小数、後者は1〜365の整数。設定変更時はDBのCommandでも検証し、不正値を422で拒否する
単位換算設定 初回は unit_gal_to_l=3.8、unit_tokan_to_l=18 に固定。一般の設定変更APIからの変更は422で拒否し、管理用移行だけで変更する

4. 権限モデル

API内部コードは lab / solvent_room_admin / global_admin とする。

機能 研究室 lab 溶媒庫管理 solvent_room_admin 全体管理 global_admin
自室の在庫・履歴参照 ○ ○ 全室
自室の入出庫・取消・訂正 ○ ○ 全室
自室の下限値・利用溶媒管理 ○ ○ 全室
自室の下限割れ・下限到達目安 ○ ○ 全室
指定数量の倍率・内訳 × 溶媒庫全体（全研究室の合算） 溶媒庫全体（全研究室の合算）
指定数量通知の参照・状態変更 × 全件 全件
溶媒マスタ参照 ○ ○ ○
溶媒マスタ登録・法令値更新 × × ○
全体設定変更 × × ○
  • rooms の1行は溶媒庫内の1研究室を表し、溶媒庫そのものの行は作らない。lab と solvent_room_admin の accounts.room_id は所属研究室のIDを必須とする。
  • 両ロールの研究室別在庫・履歴の参照と更新は所属研究室に限る。リクエストの roomId だけを信頼しない。solvent_room_admin は所属研究室に関係なく、単一溶媒庫の指定数量と通知を全件扱える。
  • global_admin の accounts.room_id は NULL とする。
  • 指定数量系エンドポイントは lab に対し常に404を返し、存在自体を表示しない。
  • GET /solvents は lab に指定数量関連のフィールドを返さない。designatedQuantity は溶媒庫管理・全体管理に限定する。
  • GET /operator-suggestions は自室の履歴から取得し、他室の実操作者名を返さない。

4-1. DBの権限境界

anon・authenticated はアプリ内の3ロールと別のDBロールである。同じ authenticated で接続する利用者を、accounts.id = auth.uid() から判定する。Route Handlerのチェックに加え、表の権限・RLSと、権限昇格するDB関数内の再認可で境界を守る。

対象クライアントの直接アクセスAPIで必要なアクセス
rooms、inventory、inventory_logsSELECTのみ付与し、RLSで研究室・溶媒庫管理は accounts.room_id の行、全体管理は全行。履歴は関連在庫の所属で判定する。未認証は不可一覧・詳細・実操作者候補も同じ研究室範囲で取得
accountsSELECTは自分の行だけ。変更は直接許可しない/me とDB関数内の所属・ロール判定
solvents認証済み全員への行SELECTポリシーを設け、非機密列だけを列単位でSELECT付与。表全体のSELECTは与えず、designated_quantity 等の指定数量関連列は直接読ませない。書き込みは不可通常のマスタ参照は公開列。管理者の法令値参照・更新は認可付きRPC
settings、notifications、operation_audits、command_requests直接SELECT・DMLを許可しない換算値等の必要な設定だけを返す限定Query RPC、管理者向け通知・設定Query RPC、認可付きCommand RPC。内部状態の dq_arm_over と再送記録は直接返さない
private.designated_quantity_statusData APIの公開スキーマに含めず、クライアントにSELECTを付与しない内部の全室集計と、溶媒庫管理・全体管理に限定したQuery RPC

業務表への直接INSERT・UPDATE・DELETEは PUBLIC・anon・authenticated から取り消す。入出庫・取消・訂正・通知対応・設定／溶媒マスタ変更は、公開スキーマの SECURITY INVOKER 入口RPCから、非公開 private スキーマの SECURITY DEFINER 実装を呼ぶ。後者は必ず auth.uid() から現在の accounts.role・room_id を読み、対象行の所属と操作種別を検証してから共通ロックと更新に進む。渡された roomId やロールを認可根拠にしない。RLSから accounts を参照する場合は、ポリシーの再帰を避ける内部ヘルパーで呼び出し元の auth.uid() を使う。関数所有者は必要な表権限に限定し、search_path = '' とスキーマ修飾を徹底する。

指定数量モニター・通知・管理者向け GET /solvents は、同じ仕組みのQuery RPCで管理者ロールをDB内でも確認する。欠品予測の roomId は絞り込み条件に過ぎず、DB関数が所属を再確認する。private はData APIの公開スキーマに加えない。authenticated に内部関数呼び出しに必要なスキーマUSAGEと個別EXECUTEだけを付与し、内部関数を直接呼ばれても同じ認可を行う。関数の既定のPUBLIC EXECUTEは取り消し、anonには実行権限を与えない。研究室向け応答・エラーには指定数量値、全室倍率、通知の有無を含めない。

権限とRLSの組み合わせ、ビュー所有者によるRLSの扱い、関数の実行権限はSupabase RLSガイド・ビューの説明・DB関数の説明に基づく。

6. 主要API詳細

6-1. 入出庫登録

POST /api/v1/inventories/{inventoryId}/movements

{
  "type": "in",
  "amount": 3.5,
  "operatorName": "山田太郎",
  "purpose": "器具洗浄",
  "occurredAt": "2026-07-10T05:30:00Z"
}
{
  "data": {
    "movement": {
      "id": "uuid",
      "type": "in",
      "amount": 3.5,
      "status": "active",
      "operatorName": "山田太郎",
      "occurredAt": "2026-07-10T05:30:00Z"
    },
    "inventory": {
      "id": "uuid",
      "amountBefore": 10.0,
      "amountAfter": 13.5,
      "baseUnit": "L",
      "isBelowThreshold": false
    }
  },
  "meta": {
    "requestId": "uuid"
  }
}

DB関数は以下を同一トランザクションで行う。

  1. セッションと accounts から操作可否を確認する。
  2. 指定数量判定専用のトランザクション単位アドバイザリロックを取得する（pg_advisory_xact_lock(1128813396, 1)）。続いて§3-4の再送キーを確保または検証し、同一要求の再送なら保存結果を返す。
  3. inventory 行を FOR UPDATE でロックする。
  4. 数量と利用状態を検証する。
  5. inventory.amount を更新する。同じUPDATE文のAFTERトリガーが、単一溶媒庫の全室合算と通知を再判定する。
  6. inventory_logs を登録し、同じトランザクションで成功結果を command_requests に保存する。

研究室ユーザーへの応答に指定数量の倍率や通知発行有無を含めない。

6-2. 履歴取消

POST /api/v1/inventory-logs/{logId}/cancel

{
  "operatorName": "佐藤花子",
  "reason": "入力する溶媒を誤った"
}
  • 対象履歴が active であることを確認する。
  • 元の change_amount を反転して在庫を戻す。
  • 戻し後の在庫が負数になる場合は409とし、管理者による棚卸調整が必要とする。
  • inventory_logs.status='cancelled' とし、operation_audits へ before/after、理由、実操作者名を登録する。
  • 在庫更新後に指定数量を再判定する。

6-3. 履歴訂正

POST /api/v1/inventory-logs/{logId}/correct

{
  "movement": {
    "type": "out",
    "amount": 1.5,
    "operatorName": "山田太郎",
    "purpose": "器具洗浄",
    "occurredAt": "2026-07-09T03:00:00Z"
  },
  "changedByName": "佐藤花子",
  "reason": "使用量の転記ミス"
}
  • 旧 change_amount と新 change_amount の差分だけを在庫に反映する。
  • 訂正後在庫が負数になる変更は409とする。
  • created_at は変更せず、業務上の発生日時 occurred_at を更新する。
  • 履歴の before/after と訂正理由を operation_audits に保存する。

6-4. 在庫下限値変更

PATCH /api/v1/inventories/{inventoryId}/low-stock-threshold

{
  "threshold": 5.0,
  "operatorName": "山田太郎",
  "reason": "安全在庫量の見直し",
  "expectedLastUpdated": "2026-07-10T05:30:00Z"
}
  • threshold は0以上または null（未設定）。
  • expectedLastUpdated と現在値が一致しない場合は 409 VERSION_CONFLICT。
  • 変更前後、理由、実操作者を operation_audits に記録する。
  • 変更後の下限割れ状態はレスポンスに返すが、notifications は作成しない。

6-6. 通知状態変更

PATCH /api/v1/admin/notifications/{notificationId}/status

{
  "status": "resolved",
  "operatorName": "山太郎",
  "reason": "保管量を調整し、倍率を確認した"

  • 許可する状態遷移は unread -> acknowledged -> resolved または unread -> resolved とする。
  • resolved への変更は reason 必須。
  • 状態変更を operation_audits に記録する。
  • 現在倍率が低下していなくても、管理者の判断で resolved にできる。

6-7. 残量推移・下限到達目安

GET /api/v1/inventories/{inventoryId}/trend?period=30d

APIは対象在庫・研究室の存在と閲覧権限を先に確認し、権限外または存在しないIDを404にする。欠品予測RPCの空結果は、認可済みの在庫について「予測できない」と解釈する。RPCも所属を再確認する。

P0で実績の残量点列、下限値、平均出庫量、下限到達目安のフィールドを提供する。予測に必要な下限値はP0で設定できるようにする。

応答には以下を含める。

  • 初期在庫を起点として期間内の有効な入出庫履歴から再構成した残量点列
  • 現在残量と下限値
  • 直近 forecast_window_days の平均出庫量
  • 下限到達目安日、または表示不可理由
  • 表示不可理由は no_outbound_history / threshold_not_set / already_below_threshold / inactive / beyond_horizon（下限到達が365日超） とする

残量点列は max(期間開始, inventory.opened_at) に、opening_amount とその時刻より前の有効な入出庫差分の合計を開始残量として置く。記録開始前の点は返さない。期間内の有効な履歴は occurred_at（実際の入出庫日時）で配置し、同時刻なら created_at、id の順で安定して並べる。履歴がまだない在庫も初期在庫から現在まで水平な実績線を返す。予測の直近N日も occurred_at で判定する。後日登録・日時訂正はその発生日時の点と予測期間に反映し、created_at はDB記録日時として変更しない。occurred_at が opened_at より前の入出庫は422とする。

7. DB更新の原子性

以下は必ずDB関数または同一DBトランザクションで実行する。

操作 同時に成功・失敗させる処理
入出庫 在庫更新、履歴登録、指定数量判定
履歴取消 履歴状態変更、在庫再計算、監査追加、指定数量判定
履歴訂正 履歴変更、在庫再計算、監査追加、指定数量判定
在庫下限値変更 下限値変更、監査追加
利用停止・再開 利用状態変更、監査追加、指定数量判定
通知状態変更 状態変更、監査追加
設定変更 設定更新、監査追加、必要な再判定
溶媒マスタ変更 マスタ更新、監査追加、指定数量を変更した場合の単一溶媒庫の合算再判定

7-1. 指定数量判定の同時更新

単一溶媒庫の倍率と通知状態を変え得る書き込みは、すべて同じロックを最初に取得し、READ COMMITTED の同一トランザクションで更新と再判定を行う。対象は入出庫、履歴取消・訂正、在庫作成・数量編集・利用停止/再開・溶媒変更、溶媒マスタの指定数量値変更、通知状態変更、初期データ投入である。設定値 dq_arm_over は再判定処理だけが変更する。

異なる研究室の在庫行は互いの FOR UPDATE では直列化されない。共通ロック取得後に在庫を更新し、文単位の AFTER トリガーが確定済みの先行更新を含む全室合算を読み直す。指定数量値の変更も溶媒マスタのトリガーで判定する。公開API用DBロールの対象表への直接書き込みを禁止し、認可付きCommand RPCを通す。管理用の移行・投入処理も同じ手順に従う。詳細はデータ設計 §2-2〜2-3を参照する。
