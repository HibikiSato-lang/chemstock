本書は ER図、UI案、DXコア機能 要件定義、 DXコア機能 データ設計 に対応するAPI設計である。 フロントエンドからSupabaseテーブルを直接更新せず、在庫、履歴、監査、通知判定の整合性をAPIとDBトランザクションで保証する。

1. 対象範囲

P0：初回リリース対象

  • ログイン中アカウントと研究室・溶媒庫の紐付け
  • 在庫一覧・詳細・入出庫登録
  • 入出庫履歴の取消・訂正・監査
  • 有効な入出庫履歴から再構成する実績の残量推移
  • 在庫下限値の設定、自室の下限割れ状態表示・下限到達目安のホーム・グラフへの追加
  • 溶媒庫単位の指定数量監視、通知履歴、未確認件数
  • 指定数量1.0以上でのアプリ内通知、未確認件数、状態管理
  • 指定数量監視に必要な溶媒マスタ参照と全体設定の変更・監査

P1：P0安定後に追加する対象

  • 在庫の利用状態の管理
  • 研究室別の利用溶媒管理
  • 全体管理者による溶媒マスタ登録・更新
  • 指定数量超過時の管理者向けメール通知（追加時期・送信先は未決定）

P1の既存APIは本書で先に設計する。メール通知の方式は送信先を確認してから設計する。DX構想の方針に従い、P1の完了をP0リリースの条件にしない。

対象外

  • 発注・購買の提案または自動化
  • 通知エスカレーション
  • 監査レポート自動生成
  • SDS連携、保管期限管理、異常検知
  • 高度な需要予測や補充推奨

2. 設計方針

2-1. 構成

flowchart LR
    UI["Next.js画面"] --> API["Route Handler<br/>/api/v1/*"]
    API --> AUTH["認証・権限確認"]
    AUTH --> QUERY["参照クエリ"]
    AUTH --> RPC["Supabase DB関数<br/>原子的な更新"]
    QUERY --> DB[("PostgreSQL")]
    RPC --> DB
    DB --> TRIGGER["指定数量再判定"]
    TRIGGER --> NOTIFY["notifications"]
    NOTIFY --> APPNOTICE["通知一覧 / 未確認バッジ"]
  • Route Handlerは入力検証、セッション取得、応答整形を担当する。
  • 在庫を変更する処理はDB関数にまとめ、在庫更新と履歴登録の片方だけが成功する状態を作らない。
  • RLSはAPIの権限確認とは別に設定し、誤実装時のデータ露出を防ぐ。
  • 通常のユーザー向けRoute Handlerはセッションに紐付くSupabaseクライアントを使い、service roleでRLSを迂回しない。
  • 指定数量が0.8以上1.0未満の場合はモニターの接近表示のみ、1.0以上の場合はアプリ内通知を作成する。
  • 初回はアプリ内通知のみとする。メール通知は初回後の追加候補で、送信先と方式を決めてから設計する。

2-2. 業務上の決定

項目 APIでの扱い
在庫を超える出庫 409 INSUFFICIENT_STOCK。在庫を0に丸めない
取消・訂正 物理削除せず、履歴の状態変更と監査記録を同一トランザクションで行う
実操作者 共有アカウントと分け、更新系APIで手入力を必須とする
単位 APIは常に solvents.base_unit の数値を入出力する。表示単位への変換は画面側
利用停止 在庫量が0でない場合は 409 INVENTORY_NOT_EMPTY。指定数量集計から実在庫が漏れることを防ぐ
在庫下限 notificationsは作らず、自室のホーム・在庫・グラフに現在状態を表示する
指定数量 rooms.kind='溶媒庫' の在庫のみ合算し、研究室ユーザーへは値も通知も返さない
指定数量通知の再発行 同一溶媒庫・同一種別の未対応通知がある間は抑止。対応済後は倍率が一度1.0未満に戻り、再び1.0以上になった時に新規通知を発行
下限到達日 UIでは「直近N日と同じペースなら」とする目安。発注提案は返さない

3. 共通仕様

3-1. ベースURLとデータ形式

  • ベースURL：/api/v1
  • 認証：Supabase AuthのセッションCookie
  • Content-Type：application/json
  • ID：UUID文字列
  • 日時：ISO 8601、UTCで送受信
  • 数量：JSON number、基準単位で小数第2位まで
  • 表示名・列挙値：APIでは安定した英語コードを返し、日本語表示はUIで変換する

3-2. 成功応答

{
  "data": {},
  "meta": {
    "requestId": "uuid"
  }
}

一覧は meta.nextCursor を使ったカーソルページングとする。 limit の既定値は20、上限は100とする。

3-3. エラー応答

{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "現在庫を超える数量は出庫できません。",
    "field": "amount",
    "requestId": "uuid"
  }
}
HTTP 主な用途
400 JSON不正、クエリ不正
401 未ログイン
403 権限不足、他室へのアクセス
404 対象なし。権限外データも情報露出防止のため原則404
409 在庫不足、取消済、バージョン競合、利用停止中
422 必須不足、数量範囲不正、不正な状態遷移
500 予期しない内部エラー

3-4. 重複実行防止

在庫を変更するAPIは Idempotency-Key: <uuid> を必須とする。 同じキーの再送は既存の処理結果（同一movementまたはaudit ID）を返し、在庫と履歴を重複更新しない。

3-5. 入力検証

項目 ルール
amount 0より大きい、小数第2位まで
operatorName 1〜100文字、手入力必須
purpose 任意、500文字以下
reason 取消・訂正・利用停止・設定変更で200文字以内、必須
occurredAt 任意、既定値はサーバー時刻、未来日時は不可

4. 権限モデル

API内部コードは lab / solvent_room_admin / global_admin とする。

機能 研究室 lab 溶媒庫管理 solvent_room_admin 全体管理 global_admin
自室の在庫・履歴参照 ○ ○ 全室
自室の入出庫・取消・訂正 ○ ○ 全室
自室の下限値・利用溶媒管理 ○ ○ 全室
自室の下限割れ・下限到達目安 ○ ○ 全室
指定数量の倍率・内訳 × 自分の溶媒庫 全溶媒庫
指定数量通知の参照・状態変更 × 自分の溶媒庫 全溶媒庫
溶媒マスタ参照 ○ ○ ○
溶媒マスタ登録・法令値更新 × × ○
全体設定変更 × × ○
  • lab と solvent_room_admin の参照・更新範囲は accounts.room_id から導出する。リクエストの roomId だけを信頼しない。
  • global_admin の accounts.room_id は NULL とする。
  • 指定数量系エンドポイントは lab に対し常に404を返し、存在自体を表示しない。
  • GET /solvents は lab に指定数量関連のフィールドを返さない。designatedQuantity は溶媒庫管理・全体管理に限定する。
  • GET /operator-suggestions は自室の履歴から取得し、他室の実操作者名を返さない。

6. 主要API詳細

6-1. 入出庫登録

POST /api/v1/inventories/{inventoryId}/movements

{
  "type": "in",
  "amount": 3.5,
  "operatorName": "山田太郎",
  "purpose": "器具洗浄",
  "occurredAt": "2026-07-10T05:30:00Z"
}
{
  "data": {
    "movement": {
      "id": "uuid",
      "type": "in",
      "amount": 3.5,
      "status": "active",
      "operatorName": "山田太郎",
      "occurredAt": "2026-07-10T05:30:00Z"
    },
    "inventory": {
      "id": "uuid",
      "amountBefore": 10.0,
      "amountAfter": 13.5,
      "baseUnit": "L",
      "isBelowThreshold": false
    }
  },
  "meta": {
    "requestId": "uuid"
  }
}

DB関数は以下を同一トランザクションで行う。

  1. セッションと accounts から操作可否を確認する。
  2. inventory 行を FOR UPDATE でロックする。
  3. 数量と利用状態を検証する。
  4. inventory.amount を更新する。
  5. inventory_logs を登録する。
  6. 溶媒庫の場合は指定数量を再判定する。

研究室ユーザーへの応答に指定数量の倍率や通知発行有無を含めない。

6-2. 履歴取消

POST /api/v1/inventory-logs/{logId}/cancel

{
  "operatorName": "佐藤花子",
  "reason": "入力する溶媒を誤った"
}
  • 対象履歴が active であることを確認する。
  • 元の change_amount を反転して在庫を戻す。
  • 戻し後の在庫が負数になる場合は409とし、管理者による棚卸調整が必要とする。
  • inventory_logs.status='cancelled' とし、operation_audits へ before/after、理由、実操作者名を登録する。
  • 在庫更新後に指定数量を再判定する。

6-3. 履歴訂正

POST /api/v1/inventory-logs/{logId}/correct

{
  "movement": {
    "type": "out",
    "amount": 1.5,
    "operatorName": "山田太郎",
    "purpose": "器具洗浄",
    "occurredAt": "2026-07-09T03:00:00Z"
  },
  "changedByName": "佐藤花子",
  "reason": "使用量の転記ミス"
}
  • 旧 change_amount と新 change_amount の差分だけを在庫に反映する。
  • 訂正後在庫が負数になる変更は409とする。
  • created_at は変更せず、業務上の発生日時 occurred_at を更新する。
  • 履歴の before/after と訂正理由を operation_audits に保存する。

6-4. 在庫下限値変更

PATCH /api/v1/inventories/{inventoryId}/low-stock-threshold

{
  "threshold": 5.0,
  "operatorName": "山田太郎",
  "reason": "安全在庫量の見直し",
  "expectedLastUpdated": "2026-07-10T05:30:00Z"
}
  • threshold は0以上または null（未設定）。
  • expectedLastUpdated と現在値が一致しない場合は 409 VERSION_CONFLICT。
  • 変更前後、理由、実操作者を operation_audits に記録する。
  • 変更後の下限割れ状態はレスポンスに返すが、notifications は作成しない。

6-5. 指定数量モニター

GET /api/v1/admin/designated-quantity?roomId={roomId}

{
  "data": {
    "room": {
      "id": "uuid",
      "name": "溶媒庫"
    },
    "totalRatio": 0.84,
    "state": "warning",
    "warningRatio": 0.8,
    "breakdown": [
      {
        "solventId": "uuid",
        "solventName": "アセトン",
        "amount": 120,
        "baseUnit": "L",
        "designatedQuantity": 400,
        "ratio": 0.3
      }
    ],
    "unconfiguredSolvents": [],
    "openNotificationCount": 2
  },
  "meta": {
    "requestId": "uuid"
  }
}

state は normal / warning / exceeded とする。 unconfiguredSolvents には在庫量が0より大きく、designated_quantity が未設定の利用中溶媒を返す。

6-6. 通知状態変更

PATCH /api/v1/admin/notifications/{notificationId}/status

{
  "status": "resolved",
  "operatorName": "山太郎",
  "reason": "保管量を調整し、倍率を確認した"
}
  • 許可する状態遷移は unread -> acknowledged -> resolved または unread -> resolved とする。
  • resolved への変更は reason 必須。
  • 状態変更を operation_audits に記録する。
  • 現在倍率が低下していなくても、管理者の判断で resolved にできる。

6-7. 残量推移・下限到達目安

GET /api/v1/inventories/{inventoryId}/trend?period=30d

P0で実績の残量点列、下限値、平均出庫量、下限到達目安のフィールドを提供する。予測に必要な下限値はP0で設定できるようにする。

応答には以下を含める。

  • 期間内の有効な入出庫履歴から再構成した残量点列
  • 現在残量と下限値
  • 直近 forecast_window_days の平均出庫量
  • 下限到達目安日、または表示不可理由
  • 表示不可理由は no_outbound_history / threshold_not_set / already_below_threshold / inactive とする

7. DB更新の原子性

以下は必ずDB関数または同一DBトランザクションで実行する。

操作 同時に成功・失敗させる処理
入出庫 在庫更新、履歴登録、指定数量判定
履歴取消 履歴状態変更、在庫再計算、監査追加、指定数量判定
履歴訂正 履歴変更、在庫再計算、監査追加、指定数量判定
在庫下限値変更 下限値変更、監査追加
利用停止・再開 利用状態変更、監査追加、指定数量判定
通知状態変更 状態変更、監査追加
設定変更 設定更新、監査追加、必要な再判定
溶媒マスタ変更 マスタ更新、監査追加、指定数量を変更した場合の関連溶媒庫再判定

8. API設計から必要となるデータ設計の補強

以下は実装前に ER図 とマイグレーションへ反映する。

対象 補強内容 理由
accounts id を auth.users.id と紐付ける セッションから所属室とroleを確定する
inventory_logs created_by_account_id、occurred_at、request_id UNIQUE、updated_at を追加 共有アカウントと実操作者の両方、業務日時、再送安全性を保存する
operation_audits account_id、request_id UNIQUE を追加し、target_id をtext型にする UUID対象と settings.keyの両方を監査する
inventory last_updated を更新時に必ず更新する 競合検知と画面の最終更新表示に使う
外部キー on delete cascade を restrict へ変更 物理削除で在庫・履歴が連鎖消失することを防ぐ
列挙値 role、履歴状態、通知種別、通知状態にCHECK制約を追加 不正な状態をDBで防ぐ
RLS 研究室・溶媒庫・全体管理のポリシーを全対象テーブルに設定 APIを迂回したデータ参照・更新を防ぐ

9. 未決定事項と暫定値

事項 本設計での暫定値
研究室の保有を指定数量に含めるか 含めない。溶媒庫のみ
指定数量通知の到達手段 初回は1.0以上でアプリ内通知を作成。メールは初回後の追加候補で、時期・送信先・方式は未決定
下限到達目安の参照日数 30日。settings.forecast_window_days で変更可能
在庫超過出庫 拒否する。差異は将来の棚卸調整機能で扱う
在庫下限の到達手段 コア要件定義§2.1を優先し、通知履歴は作らない
