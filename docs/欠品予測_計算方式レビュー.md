# 下限到達の見通し：計算・表示方法の再検討

- 作成日：2026-10-03
- 状態：**設計提案。現行の計算コード・要件定義は変更していない。**
- 対象：研究室×溶媒ごとの下限到達見込み。指定数量監視F1とは別の機能。

## この機能で答えたい問い

研究室が知りたいのは「統計的に計算された日付」そのものではなく、**いま残量を確認する必要があるか、次の使用や補充に備える必要があるか**である。下限は研究室が決める管理上の値であり、下限到達日はゼロ在庫日でも発注締切日でもない。[DX構想](DX構想.md)のF2は早期の気づきを目的にしている。

入出庫履歴だけでは、まだ登録していない実験予定・次回のまとめ出庫・補充リードタイムは分からない。したがって、どの平均式を使っても「次にいつ、何L使うか」は予言できない。日付を表示するなら、**過去のペースが続く場合の条件付き試算**として扱う。

## 現行実装

利用中在庫について、実際の入出庫日時`occurred_at`が直近N日（初期値30日）に入る有効な出庫履歴だけを合計する。取消済みと入庫は消費量に含めない。

```text
日平均使用量 = 直近N日の出庫量合計 / N
下限までの日数 = (現在量 - 下限値) / 日平均使用量
下限到達見込み = 現在日時 + 下限までの日数
```

下限未設定、出庫実績なし、既に下限以下、利用停止、365日超は予測日を出さない。[製品SQL](../supabase/migrations/20261003000000_release_queries.sql)と[プレビュー計算](../lib/chemstock-ui.ts)はこの方式で実装済みである。[要件定義 F2-1〜4](DXコア機能_要件定義.md)も固定N日平均と日付表示を指定し、§7では開始直後の楽観的な表示を許容している。**方式を変える場合は、この既存決定も改訂する必要がある。**

## 検討が必要な理由

| 状況 | 具体例 | 現行式の振る舞い | 運用上の懸念 |
|---|---|---|---|
| 記録開始直後 | 開始3日で3 L出庫、現在12 L、下限4 L | 30日で割ると0.1 L/日、下限まで80日 | 観測した3日だけで割れば8日となり、初期の分母の選び方で10倍違う。どちらも短期データでは信頼できない |
| まとめて出庫 | 30日で6 Lを1回だけ出庫、現在12 L、下限4 L | 0.2 L/日、下限まで40日 | 次の実験が明日なら、平均による日付は早い気づきにならない |
| 出庫なし | 最近の出庫がゼロ | 予測日なし | 「当面安全」に見えるが、予定された実験の出庫は履歴から分からない |
| 記録の欠落・訂正 | 出庫漏れ、後日登録、取消 | 記録が直れば再計算される | 記録の正確さが予測の前提。画面の数値だけで正しさは保証できない |
| 日付の丸め | 計算結果が1.2日後 | 製品SQLは現在日時に1.2日を加える | [データ設計のSQL例](DXコア機能_データ設計.md)は日数を切り上げて日付に足すため、表示日がずれることがある |

さらに、本番開始時に旧デモ履歴を引き継がない方針なので、初期は出庫履歴が少ない。[開発前の合意・準備](開発前の合意・準備.md)の前提を踏まえる必要がある。

## 推奨する初回リリースの式

**到達日を計算する式は初回リリースから外し、使用量に対して残量がどの程度あるかを計算する。** 研究室の使用が実験日に集中する場合、平均値から得た日付よりも、次の出庫で下限に届きうるかが判断に役立つ。

```text
余裕量 D = 現在量 A − 下限値 L
直近N日の最大1回出庫量 M = max(−change_amount)
同量の出庫で下限に達する回数 K = ceil(D / M)  ※ D > 0、M > 0 の場合だけ
```

対象履歴は現行実装と同じく、`occurred_at`が直近N日（初期値30日）にある`status='active'`かつ`change_amount < 0`の出庫だけとする。計算は在庫の基準単位で行う。`M`は次回の出庫量の予測ではなく、**過去に記録された最大の1回出庫量**である。`K`は「同じ量を繰り返したら」という条件付きの比較であり、実際にあと何回使えるかの保証ではない。

| 状態 | 初回リリースの表示 |
|---|---|
| 下限未設定・利用停止 | 計算しない。設定または在庫状態を示す |
| `D ≤ 0` | 「下限以下」、現在量、下限を示す |
| `D > 0`かつ期間内の出庫なし | 「下限までD L。直近N日の出庫履歴なし」と示す。「安全」とは表示しない |
| `D > 0`かつ`M > 0` | 「下限までD L。直近N日の最大出庫M Lと同じ量なら、あとK回で下限に到達」と示す。`K=1`ならホームにも注意表示する |

例えば現在12 L、下限4 L、直近最大出庫6 Lなら`D=8 L`、`K=ceil(8/6)=2`。表示は「下限まで8 L。直近の最大出庫6 Lと同じ量なら、あと2回で下限に到達」。その2回がいつ起きるかは表示しない。直近の出庫総量と出庫日数も詳細画面に添えると、`M`が1回の例外的な値か判断しやすい。

この方式は、履歴が短い在庫に「80日後」などの楽観的な日付を出さない。過去の最大出庫量も将来の使用量を保証しないため、使用予定が分かっている研究室は予定量と現在量を別途確認する必要がある。

## 日付の試算を再導入する条件

実履歴が蓄積し、一定のペースが続く在庫について、過去の時点から再計算して「早めの確認」に役立つことが確認できた場合だけ、別枠で次の条件付き試算を表示する。

```text
日平均使用量 u = 直近N日の有効な出庫量合計 / N
下限までの日数 T = D / u  ※ D > 0、u > 0 の場合だけ
```

これは現行の平均式を**適用対象を絞って残す**案である。「直近N日のペースが続けば○月頃」と明記し、確定日・発注日と呼ばない。`N日・異なる2出庫日`のような未検証の基準をここで確定しない。出庫の偏り・継続性を実データで調べ、日付を出せる条件と表示日の日付丸めを決める。**記録開始直後は観測日数で割る**という単純変更も、1回の出庫を毎日の需要と誤認するため採らない。

## リリースに向けた決め方

1. **判断したい行動を定義する。** 研究室が在庫を確認するタイミング、下限の決め方、補充に要する日数を整理する。補充リードタイムを記録していない現状では、発注締切日の算出まで広げない。
2. **初回の表示方針を決める。** 推奨は上記の`D`・`M`・`K`とし、到達日は初回リリースで表示しない。これは現行F2-1〜4と§7の変更になるため、要件定義、DB Query、プレビュー、ホーム、グラフ、受け入れ基準を同時に改訂する。「欠品予測」という名称も「下限到達の目安」などへ見直す。
3. **実データで検証する。** ある日時までの履歴だけで当時の表示を再現し、その後の実際の出庫と照合する。下限到達日の誤差だけでなく、確認の遅れ、誤った安心感、過度な早期表示、日付を出せる在庫の割合を測る。途中で補充した在庫は、そのまま「予測が外れた」と数えない。
4. **日付を採用する場合に表示を揃える。** 小数日の到達時刻と日本時間の暦日をどの粒度で示すか決め、設計書のSQL例、製品SQL、プレビュー、表示のタイムゾーンを一致させる。

実履歴に間欠的な需要が多いなら、通常の平均や高度な手法を比較できる。ただし複雑な方式だけで次の実験日が分かるわけではない。検証では未来の履歴を学習側に混ぜない。[Microsoft Learnの間欠需要の説明](https://learn.microsoft.com/en-us/dynamics365/supply-chain/demand-planning/croston-method)と[Forecasting: Principles and Practiceの時系列交差検証](https://otexts.com/fpp3/tscv.html)を参考にする。

現段階の[チーム共有ガイド](チーム共有_実装機能ガイド.html)には、現行コードで何が表示されるかと、計算方式を再検討中であることを分けて記載する。方式の変更が確定するまでは、現行の予測日をリリース妥当性の証拠にはしない。
