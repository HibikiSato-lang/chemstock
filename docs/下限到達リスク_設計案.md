## 1. 利用者に示すこと

**「補充がなく、過去と同様の出庫傾向が続くとすると、今後7日間の出庫で設定済みの下限へ達しそうか」を示す。** 7日は検証用の仮値であり、購入先の納期を意味しない。

利用者が次の使用に備えて在庫と使用予定を確認することを支える。下限値は研究室が設定した値を使う。安全在庫・発注点の自動設定、発注提案、購入量の計算、確定した到達日の表示はこの案に含めない。

計算結果は過去の出庫量を現在の余裕量に当てはめた**履歴上の割合**である。将来の確率として校正済みとは扱わない。画面では「欠品確率」「95%安全」「あと何日使える」と呼ばず、根拠と条件を併記する。

初回リリースの現在量・下限以下の状態・残量実績という範囲は維持する。本案はその後の検証・導入候補とし、設計資料の作成を予測表示の有効化とは扱わない。

## 2. 計算の考え方

### 2.1 現在の余裕量

```text
A = 計算時点の現在量
B = 計算時点の設定済み下限値
M = A - B（下限までの余裕量）
```

`M <= 0`なら既に「下限以下」であり、予測の割合は返さない。`M > 0`の在庫だけを将来の出庫量と比較する。数量はすべて基準単位で計算する。

補充がなく出庫だけで残量が減るという仮定では、「期間内に下限以下になる」条件は「期間内の累積出庫量がM以上になる」である。**一致も到達に含める（`>=`）。**

### 2.2 過去のH日間出庫量

| 記号 | 定義 |
|---|---|
| `t` | DBが1回の読み取りの基準として確定する計算日時 |
| `H` | 見通しの期間。試行では7日 |
| `W` | 参照する最大日数。試行では180日 |
| `d` | 24時間。保存・計算はUTC、表示はAsia/Tokyo |
| `O` | 記録開始と、確認できる再開後などの参照可能期間の開始のうち遅い日時。通常は`opened_at` |
| `W_eff` | `min(W, floor((t - O) / d))`。参照可能期間の完全な24時間の数 |

`W_eff >= H`なら、次の区間を1日ずつずらして作る。

```text
k = 0, 1, ..., W_eff - H
区間の終了 e_k = t - k × d
区間              (e_k - H × d, e_k]
出庫量 S_k        = 区間内の有効な出庫の -change_amount の合計
候補区間数        = W_eff - H + 1
```

1区間は必ずH×24時間とする。計算時刻と同じ時刻で区切るため、昼に実行したときの当日午前だけを「1日」として扱わない。未来側の評価範囲も `(t, t + H × d]` とする。左端を除外、右端を含む規則をDB・プレビュー・評価で揃える。

期間内に出庫がなければ、その区間の出庫量は0。ただし、記録開始前や判明している記録欠落を0で埋めない。取消済みと入庫は出庫量に含めない。訂正後の`occurred_at`と数量で再計算する。

### 2.3 比較する割合と分位点

後述の品質条件を満たす区間を残し、次を求める。

```text
N = 使用できる区間数
K = S_k >= M だった区間数
r = K / N
```

例：現在6 L、下限4 L、余裕2 L。使用できる7日間の区間が174個あり、そのうち52区間で2 L以上出庫していれば、`r = 52 / 174 ≒ 29.9%`となる。この数字は説明用の仮例であり実データの評価結果ではない。

補助情報として同じ分布の中央値・95%点・最大値を返す。分位点は昇順に並べたN個の値の`ceil(q × N)`番目（1始まり）を使い、補間しない。95%点を下限値や発注点へ自動反映しない。

注意表示の判定は`r`を丸める前に行う。`M == 95%点`の場合には同じ値が多数ある可能性があり、95%点との比較だけで到達割合を判定しない。

### 2.4 この方式が仮定すること

- 参照期間の出庫傾向が今後の比較材料になる。季節・実験計画・研究テーマの変化はv1では説明変数にしない。
- 記録対象は溶媒庫からの出庫。研究室内での実消費や未登録の必要量まで推定できるとは扱わない。
- 補充を見込まない。現在未登録の入庫予定は織り込まない。
- 区間は重なっているため、N個の独立した実験ではない。同じ1回の出庫が複数区間に入る。Nから単純な二項分布の信頼区間を作らない。

## 3. 使用するデータと品質条件

### 3.1 既存モデルとの対応

[ER図のテーブル説明](ER図.md#テーブル説明)は`inventory`を「研究室別の保有・管理対象」、`opening_amount`・`opened_at`を「推移の起点」と定義している。また、設計上の決定では「推移の開始点より前へは遡らず」「将来の棚卸調整は出庫と区別して記録」としている。本案もその定義に従う。

| 既存データ | 用途 |
|---|---|
| `inventory.id / room_id / solvent_id` | 対象と認可。研究室を混ぜて出庫分布を作らない |
| `inventory.amount / low_stock_threshold` | 現在の余裕量 |
| `inventory.opening_amount / opened_at` | 記録開始と残量照合の起点 |
| `inventory.is_active` | 現在の利用状態 |
| `inventory_logs.change_amount / status / occurred_at` | 有効な出庫の量と業務発生日時 |
| `inventory_logs.created_at` | 過去時点で記録済みだったかを評価するときに使用 |
| `operation_audits` | 訂正・取消・下限変更・利用停止/再開の追跡、過去時点の復元 |

**業務テーブル・カラムの追加はこの設計では要求しない。** 計算は読み取り時に行い、在庫・下限値・通知を変更しない。業務上の予測保存テーブルは作らず、評価用の出力は業務履歴と別に扱う。

既存の`forecast_window_days=30`は平均方式の参照設定なので、この方式の180日へ読み替えない。試行パラメータは方式の版とともにコード上で固定する。将来、管理画面から変更可能にする場合は既存の監査付き設定Commandで扱い、検証対象の版も更新する。

### 3.2 計算を停止する条件

- `opened_at`・初期在庫・日時・数量に欠落や不正がある。
- 全期間の有効な入出庫を使った`opening_amount + sum(change_amount)`と現在量が一致しない。未来日時の履歴が残高に混ざる場合も検知する。
- 判明している記録欠落、調整や他用途の移動を出庫と区別できない期間がある。
- 利用停止/再開などにより参照期間の業務上の意味が変わり、使える期間を特定できない。

記録の完全性や出庫の目的は現在のカラムだけでは自動判定できない。`purpose`の自由記述からAIで自動分類しない。現場確認で問題が見つかった在庫は試行対象から外し、その理由を評価記録へ残す。品質未確認の在庫を本番の予測対象に自動追加しない。

試行実装では、全体管理者の確認範囲を既存の監査ログに保存する。`stock_risk_command('quality', ...)`は実操作者・理由・確認開始日時・期待する在庫更新日時・期待する最新の確認監査ID（未確認はnull）を必須とし、`operation_audits`に`stock_risk_quality`として確認／対象解除を残す。最新の確認の`eligible / verifiedFrom / verifiedAt`をQuery内で取得する。全体管理者向け`stock_risk_reviews()`は表示の無効時も最新の確認状態・操作者・理由と、その読取時点の在庫更新日時を返す。確認画面を開いた時点の版を固定し、在庫または最新監査IDが変わった場合は最新の履歴を確認して入力し直す。一般利用者のQuery引数による自己申告で確認済みにしない。確認範囲を取得できない対象は`history_quality_unverified`として割合を返さない。

確認後の過去の訂正・取消・遡及登録は`created_at / updated_at / occurred_at`から判定し、`history_changed_since_review`として再確認まで割合を抑止する。通常の新しい入出庫だけでは確認を無効にしない。確認記録は在庫量・下限・指定数量通知を変更しない。記録の完全性は自動で証明できず、現場確認の内容と範囲を明示するための管理情報である。

過去の残量を復元し、在庫ゼロが継続した時間や利用停止期間が分かる場合は、それと交わる候補区間を除外する。在庫不足で出庫できなかった期間を「需要ゼロ」と学習しないためである。残量復元には入庫も含め、出庫量の合計からは入庫を除く。利用停止の履歴が復元できなければ、確認できる再開後の期間だけを使う。

除外した区間数と理由を出力する。この処理でも、記録されなかった出庫依頼や不足による実験延期は観測できない。この限界は実データ評価に残す。

### 3.3 数値表示の試行条件

以下は**検証開始用の仮値**であり、信頼性を保証する基準ではない。参照期間や注意表示の境界と合わせて評価し、最終評価期間を見る前に固定する。

| 条件 | 試行の仮値 | 目的 |
|---|---|---|
| 見通しの期間H | 7日 | 使用予定を確認する単位を固定する |
| 最大参照期間W | 180日 | 最近の出庫を使い、古い運用の影響を抑える |
| 確認できる観測期間 | 90日以上 | 記録開始直後の割合表示を抑える |
| 出庫のあった日区間 | 10区間以上 | 少数のまとめ出庫だけで割合を出すのを抑える |
| 使用できる非重複H日区間 | 12区間以上 | 重複による見かけの標本数増加を見分ける |
| ホームの注意表示 | `r >= 0.20` | 注意表示の負担と見逃しを比較するための仮の境界 |

「出庫のあった日区間」は、同じ基準時刻tから1日ずつ区切った完全な24時間の区間で数える。使用できないH日区間の除外理由に該当する日区間は数えない。

非重複区間数は`t`からH日ずつ遡った区間のうち使用可能な数とする。除外がなければ`floor(W_eff / H)`個。**これは独立性や有効標本数の推定ではない。** 除外がなければ180日の参照で候補174区間・非重複25区間、90日の参照で候補84区間・非重複12区間となる。

どの条件も満たさないうちは、現在量・下限までの余裕・不足理由だけを表示する。短い履歴を引き延ばしたり、他研究室の履歴を暗黙に流用したりしない。

## 4. 状態と表示

### 4.1 状態の優先順位

| 優先 | 状態コード | 条件・扱い |
|---|---|---|
| 1 | `inactive` | 利用停止中。予測しない |
| 2 | `threshold_not_set` | 下限未設定。割合を返さない |
| 3 | `already_below_threshold` | `A <= B`。実際の下限以下の表示を優先 |
| 4 | `data_quality_issue` | 残量不一致・欠落などにより計算できない |
| 5 | `insufficient_history` | 確認できる観測期間が90日未満、またはH日区間を作れない |
| 6 | `no_outbound_history` | 確認できる参照期間に出庫なし |
| 7 | `sparse_history` | 日区間数・非重複区間数などの表示条件を満たさない |
| 8 | `ready` | 条件を満たし、履歴上の割合を表示可能 |

`ready`以外の状態では割合・分位点・注意判定を`null`にする。下限以下を100%、履歴不足を0%へ置き換えない。不足理由は複数返せるようにする。履歴に問題があっても、既存の現在量・下限状態の表示とは区別する。

### 4.2 画面案

既存の5タブと[UI案](UI案.md)のデザイントークンを使う。在庫詳細・グラフの現在量表示の下に1つの折りたたみ項目を追加する。グラフは実績線と設定済みの下限線を使う。

```text
7日間の出庫を踏まえた見通し
現在 6.0 L ／ 下限 4.0 L
下限まで 2.0 L
過去の7日間の約30%で、2.0 L以上を出庫しています。
補充がない場合の参考として、使用予定と残量を確認してください。
[計算の根拠 ▼]
```

根拠には参照期間、`K / N`、出庫のあった日区間数、非重複区間数、除外区間数、7日間出庫量の中央値・95%点・最大値、計算日時を表示する。区間の重複と、出庫傾向の変化を反映しないことを短く説明する。画面の文言にはSQL名・方式識別子を出さない。

| 結果 | 文言・表示 |
|---|---|
| `ready`かつ`0 < r < 1` | 「過去の7日間の約X%で、M L以上を出庫」 |
| `ready`かつ`r = 0` | 「参照した7日間の区間には、M L以上の出庫はありません」。安全を示す色・文言は使わない |
| `ready`かつ`r = 1` | 「参照したすべての7日間の区間で、M L以上を出庫」。将来の確定表現にしない |
| `0 < r < 0.01` | 「1%未満」と表示し、0%へ丸めない |
| `insufficient_history / sparse_history` | 「見通しを表示するための履歴が不足しています」＋現在の余裕量 |
| `no_outbound_history` | 「参照期間に出庫履歴がありません」。当面安全とは表示しない |
| `data_quality_issue` | 「履歴の確認が必要なため、見通しを表示できません」 |
| `already_below_threshold` | 既存の「下限以下」を表示。予測行を重ねない |

ホームでは実際の下限以下を先に表示し、その後に`ready`かつ注意条件を満たす行を割合の降順で最大3件表示する。同率は在庫ID順で固定し、残りは折りたたむ。タップ先は在庫詳細。「過去の7日間出庫から、使用予定の確認が必要」という趣旨で示し、発注ボタンや発注推奨を追加しない。

割合が注意条件未満でも詳細で根拠を確認できる。ホームに行がないことが安全判定にならないよう、詳細では現在の余裕量と履歴不足理由を常に確認できる。

## 5. Query・APIの設計

### 5.1 DBから画面まで

DBの認可付きQuery RPCで、同じ読み取りスナップショットの在庫・履歴・必要な監査を集計する。単一の読み取りSQLと固定したtを使い、途中の入出庫・訂正によって現在量と出庫分布が食い違わないようにする。

計算手順は、対象の認可 → 現在状態 → 残量照合・参照可能期間 → 候補区間生成 → 品質による除外 → 日区間数などの確認 → `K / N`と分位点、の順とする。残量照合は全期間の履歴を用い、出庫分布は参照期間へ絞る。計算前に履歴一覧のページングや表示件数上限を適用しない。

研究室・溶媒庫管理者は所属研究室のみ、全体管理者は指定した対象研究室を参照できる。画面の所属・対象研究室の扱いは既存の認可設計に合わせる。引数だけで認可せずDBで`auth.uid()`と所属・ロールを照合する。研究室間の合算や指定数量関連値を応答に含めない。

実装したRPCは`public.fn_stock_risk(p_room_id uuid default null, p_inventory_id uuid default null)`で、既存の非公開スキーマ・Query RPCの認可方式に合わせる。`p_inventory_id`がある場合も`p_room_id`との所属一致を確認する。引数なしでは所属研究室（全体管理者は全研究室）の結果を返す。一般利用のRPCに過去時点の`t`を指定させず、DB時刻で計算する。旧`fn_stock_forecast`の応答型は流用しない。

新設定`stock_risk_enabled`は初期`false`。`app_settings()`に利用可否と有効状態を追加する。全体管理者の`stock_risk_command('enable', ...)`だけで試行を有効化でき、実操作者・理由・変更前後を監査する。無効時のQueryは認可確認後に空配列を返す。HTTP APIは今後の候補で、今回の画面は直接RPCへ接続する。

HTTP APIを経由する場合の候補は次のとおり。現在のアプリの直接RPC接続でも同じ計算結果・状態を使い、計算をRoute HandlerやUIで別実装しない。

```text
GET /api/v1/inventories/{inventoryId}/stock-risk
GET /api/v1/stock-risks?roomId={roomId}  （ホーム向け）
```

参照期間・注意境界などはサーバーの方式設定で確定し、利用者がURLで任意変更する設計にしない。無認証は401、存在しない対象と権限外の対象は404、計算不能な正規の在庫は200で状態を返す。設定の不正・DBエラーを「履歴不足」や空結果へ置き換えない。


数量は基準単位のJSON number、小数第2位まで。割合は0〜1で小数第6位に丸めて返し、画面の割合は整数%程度へ丸める。注意判定はDBで丸め前に行う。`K / N`を併記することで返却値の丸め前の根拠を追える。

DBの合計・差分・数量比較は`numeric`で行う。プレビュー側は数量を0.01 L単位の整数などへ変換して同じ比較を行い、浮動小数の誤差で到達判定が変わらないようにする。L/gal/斗缶の表示換算後の数値を判定へ戻さない。

`referenceDays`は実際に参照できた`W_eff`、期間は同じtを基準に返す。候補区間数と除外後の区間数を区別する。計算不能時の割合・`windowOutbound`・`needsAttention`は`null`とし、評価できない件数も`null`とする。`reasonCodes`は`history_too_short`、`too_few_outbound_days`、`too_few_non_overlapping_windows`、`ledger_mismatch`、`history_quality_unverified`など不足理由を返す。確認できた件数0と、確認できない`null`を区別する。

HTTP応答は共有キャッシュへ保存しない。入出庫・取消・訂正・下限変更・利用停止/再開後に対象研究室の結果を再取得する。画面を開く・戻る際にも更新し、計算中や取得失敗で古い結果を現在の判定として表示しない。

プレビュー計算を追加する場合は同じ区間定義・数量精度・状態判定と固定時刻を使い、DBとの共通ケースで一致を確認する。既存の旧平均方式の`Forecast`型とこの結果を混在させない。

## 6. 検証の設計

### 6.1 計算・認可・表示の受け入れ条件

| ケース | 期待結果 |
|---|---|
| 合計出庫量が余裕量に一致 | 下限到達区間としてKへ加算 |
| H日間で複数回出庫 | 回数ではなく基準単位の合計で比較 |
| 有効な出庫なし | 観測が確認できる区間は0。割合表示は出庫なし状態として抑止 |
| 記録開始から3日 | 開始前を0で埋めず、`insufficient_history` |
| 基準時刻が正午 | 端点は正午で揃い、各区間はH×24時間 |
| 出庫日時が区間の左端・右端 | 左端を除外、右端を含む |
| 入庫・取消・訂正 | 入庫と取消は出庫量へ入れず、訂正後の日時・量で再計算 |
| 在庫ゼロが継続・利用停止 | 該当時間と交わる区間を除外し、理由・件数を返す |
| 現在量と有効履歴の残高が不一致 | 予測の割合を返さない |
| 下限未設定・利用停止・下限以下 | 対応する状態を返し、割合へ置き換えない |
| K=0・K=N・割合1%未満 | 実績に沿った文言を出し、安全・確定・0%へ誤変換しない |
| 注意境界の前後、数量0.01 L差 | 丸め前の値と十進数量で一貫して判定 |
| 他研究室のID・偽のroomId | DBとAPIで拒否。存在の有無・集計値を漏らさない |
| 集計中に入出庫が確定 | 同じスナップショット内で現在量と履歴が一致 |
| 画面用履歴が200件を超える | 全件の集計結果と一致。表示ページングの影響を受けない |
| DB計算とプレビュー計算 | 固定したt・同じデータで状態・K/N・分位点が一致 |

ローカルでは合成27ケースでDB／プレビューの状態・件数・割合・分位点を比較し、権限と監査の検証を実施した。実施コマンドと画面確認の範囲は作業記録に記載する。同時実行中のQuery読み取り、実Supabase Auth／Data API、実データでの有効性は未確認である。

### 6.2 実データの時系列評価

1. 記録の範囲・欠落・休止・移動を現場確認し、使用可能な研究室×溶媒と期間を整理する。
2. 古い期間をパラメータ比較に使い、その後の連続した期間を最終評価に残す。ランダムに日を混ぜない。
3. 評価時刻`t_j`ごとに、その時点までに利用可能だった情報だけで現在量・下限・履歴を復元して計算する。
4. `(t_j, t_j + H × d]`の出庫と実際の残量を照合する。評価期間末でH日分が観測できない例は除外する。
5. 主評価はH日ずつずらした重複しない評価区間とする。毎日の評価は連続した注意表示の負担を見る補助評価に使う。

後日登録・訂正・取消による情報漏れを避ける。`occurred_at <= t_j`でも、`created_at > t_j`なら当時の入力へ入れない。`t_j`より後の訂正・取消・下限変更は監査のbefore/afterから巻き戻す。現在の`active`行を日付で絞るだけでは過去の運用を再現できない。

監査や初期記録が揃わず当時の状態を復元できない場合は、当時の予測性能を再現したと報告しない。今後の試行で計算時点の入力・設定版・出力を別の評価ファイルに保存し、その後の実績と照合する。実データ本文はGit管理へ追加しない。

### 6.3 補充・介入の扱い

本案は補充なしの見通しなので、補充後に下限へ達しなかったことをそのまま誤警報と数えない。

- 実際の下限到達を使う主要な二値評価は、H日間に入庫・数量調整・利用停止・下限変更がなく、全期間を確認できる区間に限る。
- 途中で介入があった区間は主要な二値評価から除き、理由・割合・開始時の指標を別に報告する。到達後に補充した例の到達事実も参考集計へ残す。
- 入庫が多い在庫が評価対象から偏って抜ける可能性があるため、上記の成績を全在庫の成績として一般化しない。
- 補助評価として「その後の観測出庫合計が開始時の余裕量以上か」も測れる。ただし、補充や在庫不足の影響を受けた観測値であり、補充しなかった場合の実際の残量を証明するものではない。

### 6.4 比較方式と評価指標

| 比較方式 | 同じH日間の注意判定 |
|---|---|
| 下限以下のみ | 現在の実績状態だけを表示する現行の運用 |
| N日平均 | 直近30日の平均出庫量×Hが余裕量以上か |
| 最大1回出庫 | 直近30日の最大1回出庫が余裕量以上か |
| 本案 | 履歴上の割合rが試行の注意境界以上か |

注意表示の有無について、下限到達の見逃し率、注意後に到達しなかった割合、到達前に表示できた時間、在庫ごとの注意表示日数を比較する。出せた在庫・評価区間の割合、履歴不足・品質問題で表示できなかった割合も併記する。

割合そのものについては、完全観測区間でのBrier score（`mean((r - 実際の到達0/1)^2)`）と、表示割合ごとの実際の到達割合を確認する。平均方式や最大出庫方式は確率を出さないため、確率予測の校正指標で直接の優劣を断定しない。研究室・溶媒ごとの結果と、偏りの大きい例を確認する。

Hはまず7日で固定し、W=90/180/365日、注意境界=0.10/0.20/0.30などを比較期間だけで検討する。履歴不足の境界も比較する。使用量が少なく季節性がある在庫では、単純な期間変更だけで安定するとは仮定しない。数値が選べないほど到達事例が少なければ、割合を一般利用者へ表示する段階へ進めない。

見逃しや表示負担の許容値は現場の判断と比較結果で決める。未検証の「90日・10出庫日・20%」を本番の合格条件として固定しない。

## 7. 導入までの作業

1. 実履歴の有無と品質を確認する。履歴が短ければ、正確な入出庫の蓄積と現在の残量表示を先に進める。
2. 固定時刻を入力にできる評価用計算と合成例で、区間・状態・数量・取消/訂正の扱いを確認する。
3. 実データで比較・最終評価を行い、H・W・表示条件・注意境界・文言を確定する。
4. 認可付きQuery RPC、実データ接続、プレビューを実装し、計算・認可の受け入れ条件を確認する。
5. 在庫詳細の根拠表示を試行し、読み違いと判断への有用性を確認する。ホームの注意行は表示負担の評価後に加える。
6. 採用時に要件定義F2、データ/API/画面設計、実装タスク、共有ガイドを更新する。既存の初回リリース完了と、この候補の採用・有効化を別に管理する。

## 8. 根拠と設計上の判断

- [Teunter・Duncan（2009）の原論文要旨](https://research.lancaster-university.uk/en/publications/forecasting-intermittent-demand-a-comparative-study/)は、英国空軍の間欠的な部品需要でCroston系とbootstrapを比較し、サービス水準・在庫量の観点で移動平均などを上回る結果を報告している。研究室の溶媒や、本案の単純な実績区間方式の有効性を直接示した研究ではない。
- [Shenstone・Hyndman（2005）の著者公開掲載版](https://robjhyndman.com/papers/croston.pdf)はCroston法の確率モデルの問題を検討している。Croston法の点予測だけで95%点が得られるとは扱わず、分布を扱うモデルは別の比較候補とする。最初に参照したMonashの2003年working paperと掲載版を区別する。
- [Forecasting: Principles and Practiceの時系列交差検証](https://otexts.com/fpp3/tscv.html)に沿い、未来を混ぜず過去時点から評価する。間欠的な出庫での用途を踏まえ、平均的な数量誤差だけでなく、下限到達と注意表示の指標で評価する。
- 7日間の実績区間を現在の余裕量に当てはめる方式、試行パラメータ、状態・UI・APIは**今回のChemStock向け設計判断**であり、文献によって採用や性能が保証されているわけではない。
