本書は、API設計と実装タスク一覧を実装可能なコード構成へ接続するための設計書である。ChemStockは、単一のNext.jsアプリケーションと単一のSupabase/PostgreSQLを維持しながら、業務機能ごとに内部境界を設ける。

1. 採用する構成

決定：「モジュラーモノリス + 軽量DDD + Ports and Adapters + 軽量CQRS」を採用する。マイクロサービス、イベントソーシング、全テーブルへのRepository導入は採用しない。
観点採用方針理由
配備Next.jsアプリを1つ配備4人で運用できる単純さを維持する
データベースSupabase/PostgreSQLを1つ使用入出庫・履歴・監査・通知を同一トランザクションで扱う
内部構造業務モジュール単位で分割担当分担と変更影響を明確にする
業務設計複雑な機能にDDDを適用在庫整合性、権限、指定数量、監査のルールを画面から分離する
読み書きCommandとQueryを分離書き込みは厳密に、一覧・集計は簡潔に実装する

2. モジュラーモノリスとは

はい、本設計はモジュラーモノリスである。「モノリス」は悪い意味ではなく、配備単位とデータベースが1つであることを表す。「モジュラー」は、その内部で業務境界と依存方向が守られていることを表す。

構成配備内部境界ChemStockでの採否
層だけのモノリス1つ機能同士が自由に参照しやすい採用しない
モジュラーモノリス1つ業務モジュール単位で公開APIを限定採用
マイクロサービス複数ネットワークとDBで物理分離現段階では採用しない

単にmodules/を作るだけではモジュラーモノリスにならない。次の3条件を継続的に守る。

  1. 各モジュールが担当する業務とデータを明示する。
  2. 他モジュールのinfrastructureや内部ファイルを直接importしない。
  3. 画面・Route HandlerからDBへ直接書き込まない。

3. 現状と改善対象

現状リスク移行後
Client Componentからinventoryを直接更新画面ごとに権限・業務ルールが分散するAPI Routeから入出庫ユースケースを呼ぶ
在庫更新後に履歴を別処理で登録片方だけ成功し、在庫と履歴が不一致になるDB RPCで原子的に更新する
超過出庫時に0へ丸める実際の差異が失われる在庫不足として拒否する
supabase/setup.sqlにDDLを集約環境間の変更履歴と再現性を追いにくいsupabase/migrations/を正とする
業務ロジックとUIが同じファイル単体テストが難しく、再利用時に重複するDomain/Applicationへ分離する

5. モジュール境界

モジュール主な責務主に扱うデータ代表ユースケース
access ログイン主体、role、所属室、閲覧・操作スコープ accounts 現在のActor取得、部屋スコープ判定
master-data 研究室・溶媒庫、溶媒マスター、法令値、基準単位 rooms、solvents 溶媒参照、マスター更新、部屋種別判定
inventory 現在庫、入出庫、取消、訂正、下限、利用停止 inventory、inventory_logs 入出庫登録、履歴取消・訂正、下限変更
compliance 指定数量倍率、警告判定、通知状態、関連設定 notifications、settings 倍率取得、通知生成、確認・対応済み化
reporting 在庫推移、ダッシュボード、欠品予測の参照モデル 他モジュールの読み取り結果 残量推移取得、下限到達目安取得
監査ログの扱い：operation_auditsは複数モジュールから利用する追記専用ストレージとする。ただし、監査を必要とするか、どのbefore/afterと理由を残すかは各ユースケースが決める。独立した「万能監査サービス」に業務判断を集めない。

モジュール間の連携

  • inventoryは溶媒の法令値を直接更新しない。必要な参照値だけをmaster-dataの公開Queryから受け取る。
  • complianceは在庫テーブルを自由に更新しない。在庫変更後の判定要求、または専用の集計Queryを使う。
  • reportingは読み取り専用とし、在庫状態を変更しない。
  • モジュール間ではEntityそのものではなく、ID・Command・DTO・公開されたQuery結果を受け渡す。

6. DDDの適用範囲

DDDを強く適用する部分

対象モデル守るルール
在庫InventoryStock、Quantity、Movement負数禁止、利用停止中の操作禁止、基準単位、原子的な履歴保存
取消・訂正Cancellation、Correction物理削除禁止、理由必須、before/after監査、負数化拒否
権限Actor、Role、RoomScope研究室は自室のみ、指定数量情報は管理者のみ
指定数量DesignatedQuantityRatio、WarningPolicy溶媒庫単位、DBの指定数量を正とする、警告倍率と法令基準を区別
通知NotificationStatus重複抑制、未確認→確認済→対応済、管理スコープ

簡潔に実装する部分

溶媒一覧、部屋一覧、履歴一覧、ダッシュボード集計などの参照処理は、必ずしもEntityを復元しない。ApplicationのQuery Serviceが用途別DTOを返す軽量CQRSとする。

共通言語

業務用語コード上の標準名注意点
実操作者operatorName共有ログインのアカウントとは別。手入力必須
ログイン主体actor認証、role、roomスコープを持つ
入庫・使用movement符号をUI任せにせず種別と数量で表現する
利用停止deactivate削除ではない
指定数量倍率designatedQuantityRatiowarningRatioとは別概念

8. 依存ルール

許可する依存

  • OKapp/api → モジュールの公開Application API
  • OKpresentation → applicationのDTO・Command型
  • OKapplication → domainとApplication Port
  • OKinfrastructure → Application PortとDomain型
  • OKモジュール間 → 相手モジュールのindex.tsで公開された型・Query

禁止する依存

  • 禁止Client Component → supabase.from(...).update/insert/delete
  • 禁止Domain → React、Next.js、Supabase
  • 禁止あるモジュール → 別モジュールのinfrastructure
  • 禁止Repositoryをテーブル単位で作ること
  • 禁止shared/を何でも置ける場所にすること
  • 禁止法令値、role、状態値を画面コードへ重複してハードコードすること

依存ルールはコードレビューだけに頼らず、基盤安定後にESLintのimport制約で自動検査する。

9. 処理フロー

入出庫Command

sequenceDiagram
    actor User as 利用者
    participant UI as 入出庫画面
    participant API as Route Handler
    participant Auth as Access Module
    participant UC as RegisterMovement
    participant Repo as Inventory Command Port
    participant RPC as PostgreSQL RPC
    participant DB as Database
    User->>UI: 数量・実操作者名を入力
    UI->>API: POST movement + Idempotency-Key
    API->>Auth: セッションとroomスコープ取得
    API->>UC: CommandとActorを渡す
    UC->>UC: 入力・権限・業務前提を検証
    UC->>Repo: registerMovement
    Repo->>RPC: セッション付きでRPC実行
    RPC->>DB: 指定数量用の共通ロックを取得
    RPC->>DB: 再送キーを確保・照合（同一要求なら保存結果）
    RPC->>DB: 在庫行ロック・在庫更新（トリガーで全室再判定）・履歴追加
    RPC->>DB: 成功結果を同じトランザクションに保存
    DB-->>RPC: 更新結果
    RPC-->>Repo: Result
    Repo-->>UC: Result
    UC-->>API: DTOまたはDomain Error
    API-->>UI: HTTP Response

Route HandlerはHTTP変換に限定し、在庫不足や操作可能範囲などの判断を持たない。DB RPCは行ロック、制約、原子性を保証する。指定数量に影響するCommandは共通ロック、再送キー、対象行の順に取得し、異なる研究室からの同時更新も順番に合算・通知判定する。すべての状態変更Commandで再送キーと入力をDB内で照合する。

Query

一覧・詳細・グラフはQuery Serviceから用途別DTOを返す。書き込み用Aggregateを毎回復元する必要はない。研究室別の直接参照にはRLSを通し、指定数量の全室集計・通知・法令値はDB内でも管理者を確認するQuery RPCから取得する。研究室ユーザーへ指定数量関連フィールドを返さない。

10. DBとの責務分担

責務TypeScript側PostgreSQL側
入力表現Command、値オブジェクト、形式検証型、NOT NULL、CHECK制約
認可ユースケース実行可否と返却項目表・列権限、研究室別SELECTのRLS、権限付きRPC内でのauth.uid()による所属・ロール再確認
在庫整合性在庫不足などをDomain Errorとして表現行ロック、負数防止、同一トランザクション
履歴・監査必要な理由・before/afterを要求在庫・履歴・監査を原子的に保存
指定数量管理者向けユースケースと表示文脈共通ロック取得後の全室合算、重複通知抑止
アプリ内通知管理者向け表示、未確認件数、状態遷移超過判定と通知作成を同一トランザクションで実行
重要：PostgreSQLのRPC定義はsupabase/migrations/へ置く。公開RPCはSECURITY INVOKER、権限昇格する実装と全室集計ビューはData API非公開のprivateスキーマに置き、実装内でも認可する。直接DMLと不要なSELECT・EXECUTEを取り消す。ユーザーAPIでservice roleを使ってRLSを迂回しない。指定数量通知のための外部メール基盤は設けない。

12. 段階的な移行

  1. 基盤：modules/、テスト基盤、マイグレーション、共通HTTP応答を追加する。
  2. 最初の縦切り：入出庫のDomain/Application/Infrastructure/APIを作り、既存画面の送信先だけをAPIへ変更する。
  3. 監査：取消・訂正・下限変更・利用停止を同じ境界へ移す。
  4. 指定数量：Complianceモジュール、超過時のアプリ内通知、未確認バッジを追加する。
  5. 参照処理：一覧・詳細・推移をQuery Serviceへ段階移行する。
  6. 整理：直接DB更新が残っていないことを確認し、setup.sqlをマイグレーションへ一本化する。

既存URLと画面遷移は維持する。一括改修ではなく、ユースケース単位でE2Eテストを通しながら置き換える。

13. 判断ルール

迷ったときの質問Yesの場合
この処理には業務上の不変条件があるかDomainへ置く
利用者の操作として名前を付けられるかApplication Use Caseへ置く
Supabaseや外部サービス固有かInfrastructureへ置く
HTTPや画面表示だけの関心事かappまたはPresentationへ置く
複数モジュールで本当に同じ意味か初めてshared化を検討する
1つのDBトランザクションが必要かCommand PortとDB RPCの境界を設計する
