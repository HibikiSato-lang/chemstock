# DXコア機能 要件定義（指定数量監視・欠品予測）

本書は、初回リリースに含める**指定数量監視（F1）**と**欠品予測（F2）**の要件を定める。
詳しい経緯は [DX構想](DX構想.md)、決定事項は [開発前の合意・準備](開発前の合意・準備.md) を参照する。
システム全体の要件定義（`DXプロジェクト_要件定義_非機能要件.docx`）とは別文書である。矛盾が見つかった場合は決定記録を確認し、両文書を更新してから実装する。

関連文書：[画面設計](DXコア機能_画面設計.md) / [データ設計](DXコア機能_データ設計.md) / [ER図](ER図.md) / [UI案](UI案.md)

## まず確認すること

| 項目 | 決まっていること |
|---|---|
| 管理する場所 | 単一の溶媒庫。庫内の在庫を研究室ごとに記録する。研究室の居室・実験室で保管する分は対象外 |
| F1：指定数量監視 | 全研究室の在庫を合算する。合算倍率が警告倍率（既定0.8）以上1.0未満なら管理者画面に「接近」と表示し、1.0以上なら管理者向けアプリ内通知を作る |
| F2：欠品予測 | 自研究室の出庫実績から下限に達する日を見積もり、ホームとグラフに表示する。発注は提案・自動化しない |
| 研究室ユーザー | 自研究室の在庫・予測を確認する。指定数量の倍率・通知は見られない |
| 溶媒庫管理・全体管理者 | 指定数量の合算倍率・内訳・通知を全件確認する。溶媒庫管理者が操作する研究室別在庫・履歴は所属研究室に限る |
| 初回リリースの通知手段 | 指定数量超過のアプリ内通知のみ。メール・SMS・プッシュ通知と在庫下限の通知履歴は対象外 |

**読み方：** §2で対象と表示先、§4で機能の条件、§8で確認方法を定める。`F1-*`・`F2-*` は要件 ID であり、画面設計・実装・確認時にも同じ ID を使う。

## 1. 背景・目的

- 現状、消防法の指定数量倍率の確認は人の手計算・目視点検に依存しており、漏れ・遅れが起きうる。
- 溶媒の残量把握も「見た人の経験と勘」に依存しており、欠品に気づくのが遅れる。
- 本機能により、**「記録を人が見て判断する」を「システムが判断して人に通知・提示する」に変える**
  （デジタイゼーション → デジタライゼーションへの移行。位置づけは [DX構想](DX構想.md) §1）。

## 2. スコープ

### 前提：対象は溶媒庫のみ（2026-07-19 確定）

本システムの在庫管理対象は**溶媒庫のみ**である。溶媒庫の内部は**研究室ごと**に分かれており
（`rooms` の1行＝1研究室）、在庫・入出庫はすべて「研究室×溶媒」で記録する。
研究室が自室（居室・実験室）で保管する溶媒は**対象外**（システムに記録しない）。
操作・閲覧対象の研究室は**ログインアカウント（`accounts.room_id`）から自動決定**し、研究室ユーザーに研究室選択UIは出さない。
溶媒庫管理アカウントも所属研究室を持ち、研究室別在庫・履歴の操作は所属研究室に限る。指定数量の合算・通知は全研究室分を扱う。全体管理者の`accounts.room_id`はNULLとする。
数量の単位は **L／ガロン／斗缶** を入力・表示で扱い、内部はLで保持する。換算は既存の残量調整画面と同じ **1 gal=3.8 L、1斗缶=18 L** とし、実装時は`settings`の値を使う（F2-6・ER図参照）。

### 対象

| # | 機能 | 概要 |
|---|---|---|
| F1 | 指定数量監視 | 溶媒庫全体（全研究室）で指定数量の倍数を常時集計し、しきい値超過を通知する |
| F2 | 欠品予測 | 直近の消費ペースから「下限割れ予測日」を算出し表示する |

F1・F2とも初回リリースに含める（F2は2026-09-25に初回対象と決定）。

### 対象外（本書では扱わない）

- 発注・購買の提案や自動化（[DX構想](DX構想.md) の方針として対象外）
- 通知のエスカレーション、監査レポート自動生成、SDS連携、保管期限管理（中期ロードマップ）
- 入出庫・取消・編集そのものの仕様（既存要件定義の範囲）
- **在庫下限（残量低下）の通知**：本機能では `notifications` として実装しない（上記「通知と状態表示の区別」の決定）
- **メール・SMS・プッシュ通知**：初回リリースでは実装しない。指定数量超過のメールは初回後の追加候補

### 通知と状態表示の区別（決定）

本機能で扱う「通知」は**指定数量系（管理者向け）に限る**。在庫下限（実際に `amount ≤ low_stock_threshold` となった状態）は
システム通知（`notifications` レコード）としては持たず、研究室が**自研究室のホームバナー（欠品予測 F2）**および
**在庫表示（一覧の ⚠・詳細の下限値）**で把握する。

理由：欠品予測（F2）が事後の下限割れ通知の上位互換であり、また管理者が全研究室の下限割れを監視するとノイズが大きく、
指定数量（溶媒庫全体の法令リスク）とは重要度が異なるため。

通知種別・関心事の主体・到達手段の全体像は次表を正とする。

| 種別 | 発生条件 | 見る人 | 画面での伝え方 | 通知履歴（`notifications`） |
|---|---|---|---|---|
| 指定数量接近 | 溶媒庫の倍数 ≥ warning_ratio(0.8) かつ 1.0 未満 | 溶媒庫管理・全体管理者 | 指定数量モニターの警告色 | 作らない |
| 指定数量超過 | 溶媒庫の倍数 ≥ 1.0 | 溶媒庫管理・全体管理者 | 通知一覧・未確認バッジ・指定数量モニター | 作る |
| 欠品予測（F2） | 自研究室在庫に下限割れ予測日あり | 対象研究室 | ホームバナー・グラフ | 作らない |
| 下限割れ中 | 自研究室在庫 `amount ≤ 下限` | 対象研究室 | 在庫一覧の ⚠・詳細・ホームバナー | 作らない |

## 3. 用語

| 用語 | 定義 |
|---|---|
| 指定数量 | 消防法令が危険物ごとに定める基準量。`solvents.designated_quantity` に保持 |
| 倍数 | 貯蔵量 ÷ 指定数量。複数溶媒は倍数を合算する |
| 警告倍率（warning_ratio） | 倍数がこの値**以上になったら画面上で接近表示する** ChemStock 独自のしきい値（既定 0.8）。通知発火条件ではなく、**法令基準でもない** |
| 下限割れ予測日 | 現在の消費ペースが続いた場合に在庫が `low_stock_threshold` に到達すると予測される日 |

## 4. 機能要件

### F1 指定数量監視

| ID | 要件 |
|---|---|
| F1-1 | 溶媒庫全体で、利用中（`is_active=true`）在庫の `Σ(amount ÷ designated_quantity)` を集計する（在庫はすべて溶媒庫内の研究室にあるため全在庫が対象）。`designated_quantity` 未設定の溶媒は集計から除外する |
| F1-2 | 在庫量が変化するすべての経路（入出庫・取消・編集・利用停止、**および在庫行の新規作成＝新規溶媒の初回入庫**）で再判定する |
| F1-3 | 倍数が warning_ratio（既定0.8）以上1.0未満の場合は指定数量モニターを「接近」表示にするが、通知は作らない。1.0 **以上になったら**「指定数量超過」として `notifications` に記録する（境界値ちょうどを含む＝`≥`） |
| F1-4 | 初回リリースでは指定数量超過をアプリ内通知一覧・未確認バッジ・指定数量モニターから確認できるようにする。メール・SMS・プッシュ通知は初回対象外とする |
| F1-5 | 未対応（未確認/確認済）の「指定数量超過」通知が残っている間は、新規通知を発行しない（重複抑制） |
| F1-6 | 倍数がしきい値未満に戻っても通知を自動で消さない。管理者が「対応済」にステータス変更する（変更は監査記録の対象） |
| F1-6b | **再通知はヒステリシスで制御する**：「指定数量超過」を「対応済」にした後は、倍数が**1.0未満まで一度戻り、再度1.0以上に到達したとき**にのみ再通知する。1.0以上のまま「対応済」にしても、直後の在庫変動では再通知しない |
| F1-7 | 管理者は現在の倍数・溶媒別の内訳を画面（指定数量モニター）でいつでも確認できる |
| F1-8 | 倍数・指定数量通知は**溶媒庫管理・全体管理者の全員が全件を閲覧できる**（溶媒庫は単一のためスコープ分けはない）。通知一覧・未確認バッジ・指定数量モニターも同様。**研究室ユーザーには一切表示しない** |
| F1-9 | 管理タブおよび管理者画面に**未確認件数バッジ**（`status='unread'`＝未確認の件数、F1-8のスコープ準拠）を表示する。管理者は画面で通知と現在の倍率を確認できる |
| F1-10 | 異なる研究室で在庫更新が同時に起きても、確定後の全室合算が1.0以上へ到達した場合はF1-5・F1-6bの重複抑制・再通知条件に従って判定する。通知未対応がなく再アーム済みなら「指定数量超過」を1件記録する。指定数量値の変更でも同様に再判定する |

### F2 欠品予測

| ID | 要件 |
|---|---|
| F2-1 | 在庫ごとに、実際の入出庫日時`inventory_logs.occurred_at`で判定した直近N日間（設定値、既定30日）の出庫実績（有効な `inventory_logs` の負の `change_amount`）から1日あたり平均消費量を算出する。後日登録・日時訂正も発生日時の期間に反映する |
| F2-2 | `(amount − low_stock_threshold) ÷ 日次平均消費量` から下限割れ予測日を算出する |
| F2-3 | 予測日をホーム画面のお知らせバナーおよびグラフ画面に表示する。表示対象は自研究室（自分の `room_id`）の在庫のみ |
| F2-4 | 次の場合は予測を表示しない：期間内に出庫実績がない／`low_stock_threshold` 未設定／既に下限割れ／到達が365日超。**既に下限割れの在庫はホームバナーに「下限割れ中」の状態を表示する（予測日は出さない）**。これは画面表示であり、`notifications` は発行しない（上記「通知と状態表示の区別」参照） |
| F2-5 | 予測は「見通しの提示」まで。発注の提案・自動化は行わない |
| F2-6 | 予測値の算出はすべて基準単位（`base_unit`）で行い、表示時のみ単位変換する |

## 5. 非機能要件（本機能に固有の分）

| 項目 | 要件 |
|---|---|
| 性能 | 倍数集計・欠品予測は画面表示を体感で妨げないこと（在庫・履歴データはたかだか数百〜数千件想定であり、集計クエリで十分） |
| 通知反映 | 在庫変化と同一トランザクションでアプリ内通知を作成し、次回の画面取得時に表示できること |
| 整合性 | 超過通知の判定と記録は在庫更新と同一トランザクションで行う。研究室をまたぐ同時更新でも判定漏れを起こさないよう、指定数量に影響する書き込みを共通ロックで直列化する |
| 監査 | warning_ratio・予測期間などの設定変更は `operation_audits` に変更前後と理由を記録する |

## 6. 制約（既存方針の継承）

- 既存画面のフロー・コードは変更しない。新機能は**差分追加**（バナーへの行追加・管理者画面への項目追加等）として実装する。
- スマホ前提・スクロール最小化（下部タブ／プルダウン／折りたたみ）。
- 指定数量・危険物分類の数値をアプリコードにハードコードしない（`solvents` テーブルの値を正とする）。
- warning_ratio(0.8) を法令基準であるかのように文言表示しない。

## 7. 運用上の前提・確認待ち

| # | 事項 | 決定・現在の扱い | 残る確認 |
|---|---|---|---|
| 1 | 研究室が自室で保管する危険物溶媒 | **対象外で確定（2026-07-19）**。自室保管分は記録せず、溶媒庫内の全研究室分を合算する | なし |
| 2 | 予測期間N日の既定値 | 30日で開始し、運用しながら `settings` で調整する | なし |
| 3 | 在庫履歴がN日より短い場合 | 日次平均を「消費総量 ÷ N（固定）」で算出する。登録から日が浅い在庫は消費ペースを過小評価し、予測日が楽観的に出ることを許容する。表示は断定表現を避ける（F2-5） | なし |
| 4 | 初回の通知確認方法 | 管理者が次にアプリを開いた時に確認・対応する。開くまで超過に気付けないことは依頼者が2026-09-27に了承した | 実際に対応する管理者への共有・確認 |
| 5 | 指定数量超過メール | 初回後の追加候補 | 導入時期・送信先・差出人 |
| 6 | 本番開始時の履歴 | 仮の在庫・入出庫履歴は引き継がず、確認済み初期在庫から始める。出庫実績ができるまでF2の予測日は表示しない（依頼者が2026-09-27に了承） | チームへの共有・確認 |

## 8. 受け入れ時の確認項目（抜粋）

| 対応要件 | 確認する条件 | 期待する結果 |
|---|---|---|
| F1-3 | 合算倍率が0.8以上1.0未満 | モニターは「接近」表示になり、通知履歴は作られない |
| F1-3、F1-5、F1-9 | 合算倍率が1.0以上に到達 | 「指定数量超過」のアプリ内通知が1件作られ、未確認バッジに反映される |
| F1-10 | 再通知可能な状態で、異なる研究室の同時入庫により確定後の合算倍率が1.0以上に到達。または指定数量値の変更により1.0以上に到達 | 通知が1件作られる |
| F1-5、F1-6b | 通知が未対応の間に在庫をさらに操作。または1.0以上のまま通知を「対応済」にして在庫を操作 | 通知は増えない |
| F1-8 | 研究室ロールで各画面を開く | 指定数量の倍率・通知が表示されない |
| §2の権限前提 | 研究室・溶媒庫管理アカウントで入出庫・在庫・履歴画面を開く。全体管理者でも同じ操作を行う | 前者は所属研究室のみ扱える。後者は対象研究室を選択でき、確認画面で対象名が分かる |
| F2-1〜F2-4 | 直近30日に出庫実績がある在庫と、出庫実績がない在庫を比べる | 前者だけにホームで「○月○日 下限割れ予測」を表示する |
| F2-1 | 出庫を後日登録・日時訂正する | 予測の参照期間と残量推移は実際の入出庫日時で判定され、DB登録日時では判定されない |
| F2-3 | 別の研究室の在庫も存在する | 予測表示は自研究室の在庫のみに出る |
| F2-4 | 在庫が下限を割る | 通知履歴は作られず、ホームバナーに「下限割れ中」を表示する |
| F1-8 | 溶媒庫管理・全体管理者でそれぞれログインする | どちらも指定数量通知の全件を確認できる |
| F1-9 | 未確認・確認済・対応済の通知が混在する | 管理タブと管理者画面のバッジは `status='unread'`（未確認）の件数を示す |
