- 日付：2026-10-08
- 対象：`codex/stock-risk`、ベース `7f1db75` と未コミットの作業ツリー。
- 範囲：下限到達リスク、入出庫・履歴編集／取消、下限設定、管理対象の追加／再開、指定数量モニター・通知、管理設定、メール送信処理と画面の接続。
- 状態：レビューとローカル検証を完了。製品コード・DBマイグレーション・本番設定の修正はしていない。

計算の境界・数量精度・認可・監査は既存検証に通る。一方、フォームとDBの更新競合、詳細の下限状態表示、履歴日時の保持に修正すべき問題がある。下限予測は初期無効の試行機能として評価する。予測日を出さないこと、実データでの精度が未評価であることを実装不具合とは扱わない。

P1は実運用前に優先して修正すべきデータ変更の問題、P2は特定条件での動作・表示の問題を示す。コードで確認した条件とブラウザー／合成例で再現した条件を区別する。

## 修正が必要な指摘

### R1 / P1：フォームの再取得で競合検出用の版が最新値へ置き換わる

根拠：`components/chemstock-provider.tsx:74–84, 178`、`components/chemstock-app.tsx:211–217, 310`、`components/stock-risk.tsx:91–109`。

下限変更では入力値をダイアログを開いた時に保持するが、`expectedLastUpdated`は保存時の`detail.last_updated`を送る。履歴確認も入力内容を保持したまま、保存時の`stock.last_updated`を送る。フォーカス復帰・手動更新などでProviderが新しい在庫を取得すると、入力は旧状態のまま、競合検出の版だけが新しくなる。

例えば、Aが下限5 Lの画面で変更入力中にBが8 Lへ更新し、Aのフォーカス復帰で最新在庫を取得すると、AはBの更新日時を使って古い判断に基づく下限を保存できる。履歴確認でも、確認中に訂正された履歴を再確認せず、取得後の版で確認済みにできる。DB側に版照合があっても、この画面経路では競合を拒否できない。

修正案：フォーム開始時の更新日時を入力と一緒に固定する。再取得で版が変わった場合は再確認を要求し、保存時に自動差し替えしない。履歴確認は確認対象の版を明示する。

合格条件：別端末の変更→Aのフォーカス復帰→旧入力の保存で競合を拒否する。入力を確認し直した後の保存だけが成功する。今回はコード経路で確認し、実Supabaseの二端末操作は未実施。

### R2 / P1：履歴編集・取消に、利用者が確認した記録の版照合がない

根拠：`components/chemstock-app.tsx:197, 284, 324–331`、`lib/supabase/inventory-logs.ts:11`、`supabase/migrations/20260929020000_inventory_commands.sql:107–115, 158–163, 195–239`。

編集画面の数量・操作者・日時は初期値として保持される。DBは最新行をロックして更新するが、編集開始時の`updated_at`を受け取っていないため、先に保存された別の訂正を検出しない。Aが旧記録を開き、Bが操作者や日時を訂正した後、Aが数量だけ直して保存すると、Aのフォームに残る旧操作者・旧日時もDBへ送られ、Bの訂正が上書きされる。

取消も、画面で確認した後に訂正された同じIDの記録を、その変更を知らせず取り消せる。行ロックと再送キーは別の内容の変更を防ぐ版照合の代わりにならない。

修正案：履歴Queryに`updated_at`を含め、編集・取消のCommandにフォーム開始／確認時の期待版を渡す。ロック後の実際の版と不一致なら拒否する。対象・変更前後を確認画面へ提示する。

合格条件：同じ履歴への二つの訂正、訂正と取消を順に送信し、後から送る旧版の操作が競合になる。再送キーによる同じ成功操作の再送は引き続き成功する。今回はコード経路で確認した。

### R3 / P2：履歴編集が、変更していない入出庫日時の秒を切り捨てる

根拠：`components/chemstock-app.tsx:329–331`。

`datetime-local`の初期値を`.slice(0, 16)`で分までに切り詰め、保存時にはその値を新しい`occurredAt`として送る。数量や氏名だけを訂正しても、入出庫日時の秒・ミリ秒が変わる。下限予測は24時間区間の端点で出庫を分類するため、境界付近の出庫が別区間へ移ることもある。

記録開始が03:00:40、初回出庫が03:00:50の場合、編集画面の初期値は03:00:00となり、在庫開始前の日時として保存できなくなる。この初期値生成と日時比較をNodeの合成例で再現し、`blockedByStartCheck: true`を確認した。

修正案：日時未変更なら元のISO日時を送る。日時を明示的に変更した場合だけ入力を変換する。秒を編集可能にする場合も、元のミリ秒まで黙って変更しない扱いを決める。

合格条件：日時未変更の数量・氏名訂正で元の`occurred_at`が完全に保持される。記録開始と初回入出庫が同じ分でも訂正できる。

### R4 / P2：在庫詳細に「下限以下」が表示されない

根拠：`components/chemstock-app.tsx:310`、`components/stock-risk.tsx:48`。要件：[F2-4](../DXコア機能_要件定義.md)。

詳細の現在量は一律に緑で表示され、下限値との比較結果は出ない。リスク部品は`already_below_threshold`なら非表示になるため、ここでも状態が補われない。試行機能が無効でも同じ問題がある。

プレビューのアセトン詳細で、現在2 L・下限5 Lと履歴が表示され、「下限以下」の文言がないことをブラウザーの画面情報で確認した。ホーム・一覧の警告を見て詳細へ進んでも、詳細では数字を比較し直す必要がある。

修正案：現在量のすぐ下に、現在庫だけから判定する警告ラベルを追加する。リスク機能の有効／無効、履歴品質、取得成功に依存させない。

合格条件：現在量が下限と同じ／下回る場合に、ホーム・一覧・詳細・グラフの状態表示が一致する。下限未設定は区別する。

### R5 / P2：履歴確認の解除・再確認同士の競合は検出できない

根拠：`supabase/migrations/20261005000000_stock_risk.sql:230–242`、`scripts/verify_stock_risk.py:158`。

履歴確認Commandは在庫の更新日時を照合するが、確認監査を追加しても在庫の更新日時は変わらない。これは既存テストでも確認している。そのため、同じ在庫版を見た管理者Bが確認対象から外した後、古い確認画面を持つ管理者Aが確認済みを保存すると、Aの保存は競合にならず、Bの解除が最新の確認監査で上書きされる。

修正案：在庫・履歴の期待版と、最新の履歴確認監査IDの期待値を分けて照合する。監査による確認状態を変更する際は、既存の確認状態を表示し、変更を確認する。単に在庫数量を更新して履歴確認の変更を表す必要はない。

合格条件：確認済み→別管理者の解除→旧画面からの確認済み保存で競合を拒否する。最新状態を読み直した明示的な再確認は成功する。今回はコードと既存検証結果から確認した条件で、新規の競合操作試験は未実施。

### R6 / P2：プレビューの利用再開では、下限予測の参照期間がリセットされない

根拠：`components/chemstock-app.tsx:466`、`components/chemstock-provider.tsx:309–313`、`supabase/migrations/20261003010000_release_management.sql:68–77`、`supabase/migrations/20261005000000_stock_risk.sql:172–173`。

実DBの利用再開は`reactivate`監査を残し、リスク計算はその日時を参照期間の開始へ反映する。プレビューの追加・再開は`is_active`の変更だけで監査を残さないため、停止前の確認済み180日履歴をそのまま利用できる。

合成例を作り、メタノールの在庫をゼロにして再開・補充した直後の計算を比較した。再開監査なしでは`ready / referenceDays=180`、同じ入力に再開日時を加えると`insufficient_history / referenceDays=0`になった。プレビューから実装の挙動を確認する際に結果が食い違う。

修正案：プレビューの追加・再開にも、DBと同じ操作者・理由・変更前後・`reactivate`日時の監査を残す。

合格条件：停止→再開→補充のプレビュー結果が、同じ固定時刻・履歴でのDB結果と一致する。

## 下限予測の計算・導入判断

区間は同じ時刻から遡る7×24時間、左端を除外・右端を含む。出庫合計と余裕量の比較、0.01 Lの境界、取消・入庫の除外、ゼロ在庫期間の除外、確認後の履歴変更による抑止は合成検証に通った。SQLとTypeScriptの応答全体も27ケースで一致した。

既存の「下限以下」と試行の見通しを区別し、将来の到達日・確率として断定しない設計は適切。初期無効、全体管理者による有効化、操作者・理由の監査も維持したい。

7日・180日・90日・10出庫日・12非重複区間・20%の値の妥当性や、将来の下限到達を見逃さない性能は、このテストでは証明されない。[設計案の時系列評価](../下限到達リスク_設計案.md)に沿って、実履歴の品質、補充介入、注意表示の負担と表示できない在庫の割合を確認する必要がある。今回、その評価は行っていない。

性能も未測定。SQLは各在庫について全履歴のJSONを多数の区間で読み直し、全体管理者向け取得は全研究室が対象になる。実データで有効化する前に、通常規模・多い履歴でRPC時間と画面の待ち時間を測る。現在の27ケース通過から性能を保証しない。
