## 指摘への対応

| 指摘 | 修正と確認したこと |
|---|---|
| R1：再取得による期待版の差し替え | 下限変更はダイアログ開始時の在庫、履歴品質確認はフォーム開始時の在庫版・監査IDを固定。自動更新しても入力と期待版を差し替えない。不一致は保存停止または競合。品質確認には明示的な再確認・入力リセットを追加。競合エラーは下限・取消ダイアログ内にも表示 |
| R2：履歴訂正・取消の版照合欠落 | 履歴Queryで`created_at / updated_at`を取得。編集・取消の開始時の`updated_at`を`expectedLogUpdated`で送り、DBで履歴をロックした後に照合する。成功済みの同じ要求の再送は版チェック前に結果を返す |
| R3：未編集日時の秒・小数秒切り捨て | 秒を入力可能にし、未変更なら元のISO文字列をそのまま送る。元の小数秒とオフセットも保持。確認期間の開始入力では、秒未満がある開始日時を次の秒へ切り上げて開始前にならないようにした |
| R4：詳細の下限以下表示欠落 | 現在量・下限だけで状態を判定。下限と同じ／下回る場合に警告と強調した残量を表示。下限未設定・利用停止・余裕量を区別し、リスク機能の設定に依存させない |
| R5：確認解除と再確認の競合 | `expectedReviewAuditId`を必須化（未確認はnull）。在庫版に加えて最新確認監査IDをDBの共通ロック下で照合。`stock_risk_reviews()`で、試行無効時も全体管理者に確認状態・期間・日時・操作者・理由と同一スナップショットの在庫版を返す。研究室／溶媒庫管理からは取得不可 |
| R6：プレビュー利用再開の監査欠落 | 追加・再開に操作者・理由・before/afterを保存。再開の`reactivate`時刻を既存計算へ反映し、再開直後に停止前の180日を使わない。デモの在庫・履歴更新にも版を付け、初期値／保存済みデータの読取にも補う |

新しい業務テーブルは追加していない。在庫確認監査の追加によって在庫量・下限や`inventory.last_updated`を変更することもない。確認操作同士は独立した監査IDで競合を検出する。

## UIの変更

- 割合の主文を「過去180日の履歴で、7日分の出庫が余裕量2 L以上だった割合：約86%」へ変更。将来確率・安全保証ではないという説明を折りたたみの外にも表示。
- 一般利用者には全体管理者への履歴確認依頼を案内。全体管理者には現在の対象／解除状態と最後の確認情報を表示。保存成功後はフォームを閉じ、結果を表示する。
- 詳細の基本情報を折りたたみ、履歴は最新3件まで表示。対象研究室・溶媒を保持してグラフと全件履歴へ移動できる。
- ホームの下限以下を件数付きで優先表示し、4件目以降を折りたたむ。
- 全体管理者がホーム・グラフ・管理・管理対象追加で研究室を選べるようにし、変更時は数量入力・対象・フィルター・グラフ選択と管理フォームをリセットする。
- グラフの凡例に、記録点を直線で接続し記録間を補間する図であることを明記。段差線への変更は行っていない。

## 発表で使える要点

共有アカウントの在庫管理では、DBの行ロックだけでは入力途中の判断を保護できない。今回、入力を開始した版を画面で保持し、在庫・履歴・確認監査をそれぞれの版で照合した。合成履歴と一時DBでは旧版からの上書きを拒否し、再送の一度分処理を維持できた。UIでは現在の下限状態と過去の出庫に基づく参考値を区別して提示できるようにした。
