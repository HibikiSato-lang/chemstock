# 指定数量通知の同時更新対策

- 日付：2026-09-28
- 状態：要件・DB/API・実装タスク・公開条件へ設計を反映済み。製品DBへの実装は未実施。
- リポジトリ・版：ChemStock、`dxproject-2026`、ベース `63d6ca9`、未コミット。

## 目的と判断

従来の設計は在庫行をロックした後に合算倍数を読む。異なる研究室の在庫行を同時更新すると互いを待たず、各トランザクションが0.95倍と判定した後、確定済みの合算だけが1.10倍になる可能性があった。在庫と通知を同一トランザクションに置くだけでは防げない。

単一溶媒庫の指定数量判定に影響するCommandは、`READ COMMITTED` で、在庫行のロック・変更より先に同じトランザクション単位アドバイザリロックを取得する。文単位の`AFTER`トリガーが、その時点で確定した先行更新と自トランザクションの更新を合算して判定する。指定数量値変更にもトリガーを付け、通知状態変更や初期データ投入にも同じロック順序を適用する。公開API用DBロールに対象表の直接書き込みを許さないことを実装条件とした。

## 根拠と確認

- PostgreSQL公式文書：[Read Committedの可視性](https://www.postgresql.org/docs/current/transaction-iso.html)、[トランザクション単位のアドバイザリロック](https://www.postgresql.org/docs/current/explicit-locking.html)、[VOLATILE関数のスナップショット](https://www.postgresql.org/docs/current/xfunc-volatility.html)。
- PostgreSQL 17.5の一時クラスタに文書のトリガーSQLを登録した。初期0.80倍から別研究室へ0.15倍ずつ、2接続で同時入庫した結果、確定後の倍率は1.10倍、通知は1件、`dq_arm_over=false`だった。新規行へのINSERTと既存の異なる2行へのUPDATEの両方で確認した。一時クラスタは停止・削除した。
- 別の一時クラスタで、在庫0.80倍から指定数量値を変更して1.00倍にした結果、溶媒マスタのトリガーで通知が1件作られた。この一時クラスタも停止・削除した。
- `git diff --check`で空白エラーなし。これは設計と最小再現の確認であり、製品RPC・RLS・本番移行の検証ではない。

## 次の作業と限界

マイグレーションと認可付きCommand RPCへロック順序を実装する際に、直接書き込み禁止、全更新経路の網羅、同時更新テストをDB統合テストとして固定する。`REPEATABLE READ` / `SERIALIZABLE`へ変える場合は再試行を含めて再設計する。製品環境ではまだ検証していない。

## 発表・報告に使える要点

研究室別の行ロックでは溶媒庫全体の通知判定を直列化できないため、単一溶媒庫の共通ロックと更新後の再集計を設計した。一時PostgreSQL環境では同時入庫後に通知1件を確認した。製品への実装と統合検証は今後行う。
